## 实测踩到的坑（预判之外的）

1. **采样器用了 mipmap 过滤器，但图集没有 mipmap → 精灵全黑**。
   GL 里"MIN_FILTER 是 mipmap 过滤器但纹理只有一级"会让纹理**不完整**，
   采样结果是全黑且**不报任何错**。新增了 `sampler_desc_sprite()`。
   顺带修了 M2 的同类问题（`texture_create_solid` 不生成 mipmap）。

2. **`ASSERT` 与 NULL 兜底逻辑同时存在是自相矛盾的**。
   `utf8_decode` 有 `ASSERT(cursor != NULL)` 又有 NULL 兜底，
   调用方看到能传 NULL 就传了，Debug 下被断言炸掉、Release 下正常。

3. **`char` 在 MSVC 上带符号**。测试里 `*cursor == 0xB8u` 拿到的是
   `18446744073709551544`（符号扩展）。比较字节值必须显式转 `(u8)`。

4. **Tilemap 的 AABB 参数在 Y 向上时容易搞反**。
   `origin` 是左上角（Y 最大），直接当 `min` 会让剔除范围为空。

5. **`const` 参数里回写统计字段**触发 `-Wcast-qual`。
   修法是去掉那个字段 —— 函数本来就返回了提交数量。

6. **函数指针数组要求签名完全一致**，参数不同的 SDF 必须改成
   "把常量写死在函数里"。

7. **`goto cleanup` 跳过的变量未初始化**（M1/M2 踩过，M3 又踩了一次）。

## 本阶段目标

在 M2 的渲染核心之上做出可用的 2D 管线：精灵批渲染（把成千上万个精灵合并成
个位数的 draw call）、2D 相机、精灵动画与图集、Tilemap、文本渲染、
调试绘制。

本阶段的核心矛盾是 **draw call 数量**。M2 的"一个物体一次 draw"在 2D 场景下
会直接崩掉（1 万个精灵 = 1 万次 draw call）。批渲染就是把"提交顺序"
重新组织成"少量大批次"的过程。

## 本阶段验收标准

* **1 万个精灵单帧 < 16ms**（vsync 关闭、Debug 构建下也要达到）。
* 打砖块 demo 可玩：挡板、球、砖块、分数、生命、暂停、重开。
* 批渲染的 draw call 数可观测（渲染统计里能看到"1 万精灵 = N 次 draw"，
  N 应该是个位数）。
* 文本能渲染中文与英文（位图字体或 stb_truetype，二选一，说明理由）。
* 2D 调试绘制可用（线、矩形、圆、十字），供后续物理/碰撞可视化复用。
* 上层仍然不直接调 GL。
* 单元测试覆盖：图集 UV 计算、批渲染的断批条件、精灵变换、2D 相机。

## 本阶段技术约束

* 纯 C11，不引入新依赖（文本渲染允许 stb_truetype，属于已批准的单头库）。
* 复用 M2 的 `renderer_push_item` / 渲染队列 / `pipeline_desc_t`，
  **不要绕过渲染队列直接调后端**。
* 复用 M0 的坐标系约定（深度 [0,1]、右手系、相机看 -Z）。
* 2D 相机的 `mat4_ortho_2d` 已在 M0 提供，直接用。
* 不提前实现 M5 的 ECS（本阶段用简单的数组/池管理精灵即可）。

## 我预判的坑（请逐条确认或纠正）

1. **断批条件**：批渲染必须在以下情况 flush：
   纹理切换、管线切换、顶点/索引缓冲写满、混合模式变化。
   其中"纹理切换"最容易漏 —— 同一图集内的精灵可以合批，
   换图集就必须断。

2. **动态顶点缓冲的更新策略**。
   每帧 `glBufferData(NULL)` 再 `glBufferSubData`（orphaning）能让驱动
   分配新的一块，避免"GPU 还在读旧数据而 CPU 已经改写"造成的隐式同步。
   但 orphan 太频繁也会浪费。需要说明选哪种策略。

3. **图集的采样渗色（texture bleeding）**。
   相邻精灵在图集里挨着，双线性采样会在边缘采到隔壁精灵的像素 ——
   表现为精灵边缘出现一圈别的颜色。
   解决办法：图集里给每个精灵留 1-2 像素 padding，或用
   `CLAMP_TO_EDGE` + 半像素 UV 内缩。两者都要说明。

4. **半像素偏移**。
   正交投影下，如果精灵的世界坐标恰好落在像素边界上，光栅化规则会让
   一半的像素采样到"半个像素"，表现为精灵模糊或边缘缺一列。
   2D 相机需要做 `floor(pos * scale) / scale` 之类的像素对齐。

5. **2D 精灵不要用 z 值排序**。
   用 z 排序会导致"同一层的精灵因为浮点误差偶发闪烁"。
   应该用 `render_layer` + 提交顺序（渲染队列的 `sequence` 已经保证了确定性）。

6. **顶点格式要紧凑**。
   2D 精灵不需要法线。用 `pos.xy`（2×f32）+ `uv`（2×f32）+ `color`（u32 RGBA8）
   = 20 字节，而不是 M2 的 32 字节 `mesh_vertex_t`。
   1 万个精灵省下 120KB/帧的带宽。

7. **索引缓冲可以复用**。
   所有精灵都是 quad，索引永远是 `0,1,2, 0,2,3`（偏移 4×N）。
   预生成一批固定索引，每帧只更新顶点数据即可 —— 省掉一半的上传量。

8. **文本渲染的基线、行高、字距**。
   `stb_truetype` 给的是字形的位图与度量，但"从哪一行开始画""行间距多少"
   要自己定。中文字体还有"全角/半角"与"字距为 0"的问题。

9. **stb_truetype 的字形缓存**。
   每个字形都要光栅化一次并放进图集，不能每帧重新生成。
   图集满了还要能重建（清空 + 重新打包）。

10. **打砖块的球与挡板碰撞**。
    高速球会"穿墙"（一帧内跨过砖块）。需要连续碰撞检测或子步进。
    这是 M3 的 demo 就会遇到的物理问题，不要求做完整物理，但要求不穿墙。

11. **`mat4_ortho_2d` 的深度约定**。
    M0 已经定死：`mat4_ortho_2d` 让 z=0 落在深度 0.5 上。
    2D 精灵如果都用 z=0，深度测试必须关闭或设为 `ALWAYS`，
    否则同深度会互相遮挡。

12. **批渲染的顶点数据要按"提交顺序"排列**。
    渲染队列会按 layer + 深度排序，但批渲染器内部的顶点顺序必须与
    排序后的顺序一致，否则同一批次内精灵的前后关系会错乱。
