> 记录 M3 阶段所有"为什么这么做"以及踩过的坑。
> 改 M3 的代码前先读这里；改动后如果推翻了某条决策，请把这一条也一起改掉。

## 一、批渲染：M3 的核心

### 1.1 要解决的问题

M2 的"一个物体一次 draw"在 2D 场景下直接崩掉：
1 万个精灵 = 1 万次 draw call，每次 draw 的 CPU 开销（状态校验、命令写入）
就有几微秒，光这一项就超过 16ms 的帧预算。

批渲染把"1 万次 draw"压成"个位数 draw"。

**实测结果**（Release，1280x720，关闭 vsync）：

| 精灵数 | 帧时间 | 绘制调用 | FPS |
|---|---|---|---|
| 10,000 | 0.925 ms | 3 | 1081 |
| 50,000 | 3.284 ms | 3 | 304 |

3 次 draw call 的构成：精灵图集 1 次 + 字体图集 1 次 + 调试绘制 1 次。
**1 万个精灵本身只占 1 次 draw call。**

### 1.2 断批（flush）的判定条件

只有满足以下全部条件的精灵才能进同一个批次：

| 条件 | 原因 |
|---|---|
| 同一纹理 | 一次 draw 只能绑定一组纹理 |
| 同一管线 | 一次 draw 只能用一条管线（着色器 + 全部渲染状态） |
| 同一 render layer | 渲染队列按 layer 排序，跨 layer 必须断开 |
| 同一深度值 | 同 layer 内按深度排序 |

任何一条不满足就必须 flush。

**"纹理切换"是最容易漏的一条**：同一图集内的精灵可以合批，换图集就必须断开，
否则精灵会采到另一张图的 UV，画面完全错乱。

实现上，管线/图层/深度都通过 `sprite_batch_set_*` 接口改变，
那几个接口自己会 flush；`sprite_batch_draw` 里只需要比较纹理。
**在 draw 里重复判断反而会漏掉"set 之后一个精灵都没画"的情况。**

### 1.3 顶点缓冲的容量是"整帧"的，不是"单批次"的

这一点很关键：所有批次共用同一块顶点缓冲，每个批次只是它的一个**索引区间**。

因为渲染队列是**帧末统一绘制**的，如果中途复用缓冲，
前面批次的顶点数据会被后面的覆盖 —— 表现为"只有最后一批精灵画对了"。

所以 `max_sprites` 是**一帧内能画的精灵总数**，超出会记警告并丢弃。

真正的解法是环形缓冲 + 多缓冲对象（N 个 VBO 轮转），
等真有"一帧几十万精灵"的需求再做。

### 1.4 顶点格式：20 字节而不是 32

```
offset 0  : POSITION   FLOAT2   (x, y)
offset 8  : TEXCOORD0  FLOAT2   (u, v)
offset 16 : COLOR0     UNORM8X4 (RGBA8)
```

对比 M2 的 `mesh_vertex_t`（32 字节）省 37%：2D 不需要法线，
颜色用 4 字节归一化整数而不是 16 字节的 float4。

1 万个精灵省下 480KB/帧的带宽 —— 在"1 万精灵 < 16ms"这个目标下，
这类细节是能决定成败的。

### 1.5 索引缓冲一次生成、永不更新

所有精灵都是同一个 quad 模式，索引永远是 `0,1,2, 0,2,3` 加 `4*N` 的偏移。

所以索引在创建时一次生成，之后每帧只上传顶点数据 —— 上传量直接减半。

### 1.6 顶点数据用 `glBufferSubData` 局部更新

不用"重新 `glBufferData`"：重新分配会让驱动丢掉已有的缓冲对象，
每帧都做等于每帧都在申请显存。

`mesh_desc_t` 新增 `dynamic` 标志，后端据此选 `GL_DYNAMIC_DRAW` ——
这个选择会影响驱动的内存放置策略（显存 vs 系统内存），选错会让每帧更新
变成跨总线拷贝。

### 1.7 UV 的 V 轴方向

纹理坐标 `v=0` 对应上传数据的第一行（图片顶部），而世界坐标 Y 向上。

所以精灵的**下**边要采 `v_max`（图片底部）：

```
左下 -> (u_min, v_max)    右下 -> (u_max, v_max)
左上 -> (u_min, v_min)    右上 -> (u_max, v_min)
```

搞反的表现是"所有精灵上下颠倒"。

## 二、纹理图集

### 2.1 采样渗色（texture bleeding）的三层防护

相邻区域在图集里挨着，双线性采样会在边缘采到隔壁区域的像素 ——
表现为精灵边缘出现一圈别的颜色。这是 2D 渲染最常见的视觉 bug 之一。

**三层防护，缺一不可**：

1. **padding**：每个区域周围留 2 像素空位（货架打包时算进格子尺寸）。
2. **UV 半像素内缩**：`(x + 0.5) / W` 到 `(x + w - 0.5) / W`。
   这保证采样点永远落在区域内部。
3. **采样器用 CLAMP_TO_EDGE**：不用 REPEAT，避免边缘绕到图集另一边。

单独用任何一层都不够：只有 padding 时，如果 UV 恰好落在边界上仍会渗色；
只有半像素内缩时，mipmap 或各向异性过滤仍可能采到外面。

### 2.2 打包算法选货架（shelf）

| 方案 | 利用率 | 实现复杂度 |
|---|---|---|
| 网格切分 | 低（大小差异大时浪费严重） | 最简单 |
| **货架**（采用） | 70-85% | 简单 |
| 天际线 | 85-95% | 约 2 倍 |
| MaxRects | 最高 | 最复杂 |

对"精灵图集"这种大小相近的输入，货架与天际线的差距很小，
而实现复杂度差一倍。等真有"尺寸差异极大的图集"需求再换。

**已知限制**：货架算法通常要求"按高度降序"输入。当前实现是逐个添加的，
无法预排序。对字形图集（高度相近）没问题，对混合尺寸的图集利用率会低一些。

### 2.3 图集用 UNORM 而不是 sRGB（M3 阶段的临时决定）

M2/M3 还没有渲染目标抽象，默认帧缓冲也不是 sRGB 的，
所以"纹理值 → 着色器 → 屏幕"全程都是 sRGB 编码空间。

用 sRGB 纹理会引入一次解码而输出端不编码，颜色会整体偏暗。

**M4 引入离屏渲染后**会统一成"全线性 + sRGB 帧缓冲"的管线，
届时这里改成 sRGB 即可。这个决定记在 §7 的遗留项里。

## 三、2D 相机

### 3.1 产出的是通用 `camera_t`

2D 相机是 3D 相机的一个特例（正交投影 + 固定朝向），
`camera_2d_to_camera()` 返回 `camera_t`。

这样渲染队列、剔除、uniform 上传全部复用 M2 的代码路径，
不需要为 2D 单独开一条路。

### 3.2 像素对齐是**相机**的事，不是精灵的事

正交投影下，如果精灵的世界坐标落在非整数像素上，光栅化会让边缘
落在像素中间，双线性采样之后表现为"精灵发虚"或"边缘缺一列"。

对齐策略分两层：

* **相机位置**吸附到 `1/zoom` 的整数倍（`camera_2d_snap_point`）。
  相机不动时画面清晰；相机平滑移动时按 zoom 粒度吸附，避免画面抖动。
* **精灵位置**由调用方给整数，渲染器**不做强制** ——
  平滑移动的物体本来就该落在亚像素位置，强行取整会让运动一顿一顿。

所以 `camera_2d_t.pixel_snap` 控制的是相机，不是精灵。

### 3.3 相机放在 z = +10

不是 z = 1。给 M6 的"2.5D 混合渲染"留出空间 ——
届时 3D 内容会出现在 2D 精灵的前后，近平面不能贴得太近。

## 四、文本

### 4.1 两条创建路径，同一个数据结构

| 路径 | 优点 | 缺点 |
|---|---|---|
| `font_create_bitmap8x8` | 不需要任何外部文件，永远能用 | 只有 ASCII，字号固定 |
| `font_create_from_ttf` | 任意字号、支持中文 | 需要字体文件；字形是**预**光栅化的 |

内置 8x8 位图字体来自 `third_party/font8x8_basic.h`（公有领域）。
TTF 路径用 `third_party/stb_truetype.h`。

### 4.2 预光栅化的限制是**有意的**

TTF 路径把"字符集"在创建时一次性光栅化进图集，图集大小固定。
所以创建时必须告诉它"要用到哪些非 ASCII 字符"（`extra_utf8` 参数）。

对游戏 UI 来说这是合适的：按钮文字、菜单项、提示语都是固定的那几十个词。

**为什么不做按需光栅化**：那会让 `text_draw` 变成"可能触发 GPU 上传"的操作，
破坏"帧内零 malloc"和"绘制阶段不做资源创建"这两条约定。
真正需要"任意动态文本"（玩家昵称、聊天）时，需要图集增长 + 重新上传 ——
那是 M7 资源层之后的事。

### 4.3 文本就是"一串按字形排版好的精灵"

所以它直接跑在批渲染器上。一段文字（同一个字体）只占一次 draw call。

排版要自己算的三件事：
1. **基线**：字形位图的左上角相对笔位置的偏移由 font 提供，
   笔位置本身沿基线前进。换行时笔位置下降 `line_height`。
2. **行间距**：`line_height + line_spacing`。中文字体的默认行高往往偏大，
   所以 `line_spacing` 允许为负。
3. **中英混排**：中文字形的 advance 通常是全角，英文是半角。
   混排时字距不齐是**正常的**，不要试图平均化。

### 4.4 描边要画 8 个方向

只画 4 个方向（上下左右）时，斜向的笔画之间会露出缝隙。
8 个方向（含 4 个对角）才能把轮廓完全盖住。

## 五、调试绘制

### 5.1 用精灵画线段，不用 `GL_LINES`

| 方案 | 问题 |
|---|---|
| `GL_LINES` + `glLineWidth` | core profile 下很多驱动忽略 > 1 的线宽；线宽以像素为单位、不随相机缩放 |
| **精灵 + 1x1 白纹理**（采用） | 完全可控，且与游戏内容共用同一条渲染路径 |

用精灵实现还有一个好处：调试图形与游戏内容共用同一个批次管理器，
不会出现"调试绘制把批次打断了，性能数据失真"的情况。

### 5.2 线段 = 一个细长的旋转精灵

中心在中点，尺寸 `(length, thickness)`，旋转角 `atan2(dy, dx)`。

圆 = N 段线段（或 N 个细长四边形拼的近似实心圆）。
箭头 = 一条线段 + 两条短线。

## 六、本阶段踩到的坑

### 6.1 采样器用了 mipmap 过滤器，但图集没有 mipmap → 精灵全黑

GL 里如果 `MIN_FILTER` 是 mipmap 过滤器、纹理却只有一级，
纹理会是"**不完整**"的 —— 采样结果是**全黑**，而且不报任何错。

图集不生成 mipmap（精灵通常按原始尺寸绘制，mipmap 只会让边缘更模糊、
还会加剧渗色），所以采样器必须用 `SAMPLER_MIPMAP_NONE`。

新增了 `sampler_desc_sprite()` 预设，并在测试里断言它与
`sampler_desc_default()` 的 mipmap 设置不同。

**顺带修了 M2 的一个同类问题**：`texture_create_solid` 原本
`generate_mipmaps = false`，配上默认的三线性采样器就会全黑。
现在改成始终生成 mipmap（1x1 的 mipmap 是 no-op，但让纹理"完整"了）。

### 6.2 `ASSERT` 与 NULL 兜底逻辑同时存在是自相矛盾的

`utf8_decode` 原本是：

```c
ASSERT(cursor != NULL);
if (cursor == NULL || *cursor == NULL) { return 0; }
```

调用方看到"这个函数能处理 NULL"就会放心地传 NULL，
然后在 Debug 构建里被断言炸掉，Release 里又正常。

**二选一**：要么断言且不兜底，要么兜底且不断言。这里选后者
（处理不可信文本的工具函数，NULL 安全是合理的）。

### 6.3 `char` 在 MSVC 上是**带符号**的

测试里写 `EXPECT_EQ_U64(*cursor, 0xB8u)`，实际拿到的是
`18446744073709551544` —— 因为 `*cursor` 是 `char`（-72），
转成 `u64` 时符号扩展了。

比较字节值时必须显式转 `(u8)`。

### 6.4 `goto cleanup` 跳过的变量未初始化（M1/M2 踩过，M3 又踩了一次）

clang 报 `-Wsometimes-uninitialized`。
所有会被 `cleanup` 用到的变量必须声明在第一个 `goto` 之前并初始化。

### 6.5 Tilemap 的 AABB 参数在 Y 向上时容易搞反

`tilemap_draw` 内部要构造一个 AABB 传给 `tilemap_draw_visible`。
但地图的 `origin` 是**左上角**（世界 Y 最大的那一边），
所以矩形是 `(origin.x, bottom)` 到 `(right, origin.y)`。

直接用 `origin` 当 `min` 会让 `min.y > max.y`，剔除范围算出来是空的。

### 6.6 函数指针数组要求签名完全一致

`static const shape_sdf_fn functions[] = {sdf_box, ...}` 里的 `sdf_box`
原本带一个 `half` 参数，与其它 SDF 的签名不一致，直接编译失败。

修法是把参数不同的 SDF 改成"把常量写死在函数里"。

### 6.7 `const` 参数里回写统计字段

`tilemap_draw_visible` 原本会往 `map->drawn_last_frame` 写统计，
但参数是 `const tilemap_t *` —— 需要 `(tilemap_t *)` 去 const，
触发 `-Wcast-qual`。

修法是**去掉那个字段**：函数本来就返回了提交数量，
调用方需要统计自己存就行。为了一个便利字段去破坏 const 契约不值得。

## 七、M3 遗留问题 / 已知代价

| 项 | 现状 | 计划 |
|---|---|---|
| 图集用 UNORM 而非 sRGB | 与 M2 的 sRGB 纹理不一致 | M4 引入离屏渲染后统一 |
| 顶点缓冲不支持环形复用 | 容量是整帧上限，超出丢弃 | 真有超大场景需求时做多缓冲轮转 |
| 字体不支持按需光栅化 | 必须在创建时声明用到的字符 | M7 资源层之后 |
| 货架打包不支持预排序 | 混合尺寸图集利用率偏低 | 需要时换天际线 |
| Tilemap 只支持等距网格图集 | 不支持任意图集区域 | M7 或按需 |
| 无 2D 视锥剔除集成 | `sprite_intersects_rect` 有了，但批渲染器不自动剔除 | M5 的 ECS + 场景层 |
| 无精灵动画系统 | 只有 sprite，没有帧序列/状态机 | M3 之后的独立小模块，或 M5 |
| 无文本自动换行 | 只支持显式 `\n` | 按需 |
| 采样器缓存 16 个槽位 | 轮转覆盖 | 够用 |

## 八、给后续阶段的提醒

1. **M4 引入离屏渲染时，把 sRGB 管线一次性理顺**：
   sRGB 颜色纹理 + 线性光照 + sRGB 帧缓冲（`GL_FRAMEBUFFER_SRGB`）。
   现在 2D 用 UNORM、3D 用 sRGB 的混合状态是 M3 的临时妥协。
2. **2D 精灵的排序不要改用 z 值**。`render_layer` + 提交顺序已经能表达
   所有 2D 需要的前后关系，用 z 只会引入浮点误差导致的偶发闪烁。
3. **批渲染器的容量要在应用初始化时给够**。超出会丢弃精灵并记警告 ——
   这个警告在日志里出现就说明要调大 `max_sprite`。
4. **新增图集时必须用 `sampler_desc_sprite()`**，不要用默认采样器
   （mipmap 不匹配 → 全黑）。
5. **`extra_utf8` 里要包含界面上会用到的所有非 ASCII 字符**。
   漏了的话那个字显示为空白（`font_glyph` 返回 NULL）。
6. **调试绘制记得 `debug_draw_begin`**，否则 `primitives` 统计会一直累加。
