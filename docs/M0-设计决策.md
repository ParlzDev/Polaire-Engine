# M0 设计决策记录

> 记录 M0 阶段所有"为什么这么做"以及踩过的坑。
> 改 M0 的代码前先读这里；改动后如果推翻了某条决策，请把这一条也一起改掉。

---

## 一、工具链与构建

### 1.1 编译器：clang（MSVC 目标），不是 MSVC 也不是 MinGW

本机情况：

| 组件 | 路径 | 版本 |
|---|---|---|
| Clang | `F:\Path\clang+llvm-23.1.1-x86_64-pc-windows-msvc\bin` | 23.1.1 |
| MSVC CRT | `D:\Program Files\Microsoft Visual Studio\18\Community` | 14.51.36231 |
| Windows SDK | `C:\Program Files (x86)\Windows Kits\10` | 10.0.26100.0 |
| CMake | `F:\Path\CMake\bin` | 4.4.3 |
| Ninja | VS 自带 | 1.13.2 |
| MinGW64（TDM-GCC） | `F:\Path\MinGW64` | 4.9.2 |

**选 clang 的理由**：

* 完整支持 C11（MSVC 的 C11 支持不完整：没有 `threads.h`，`_Generic`/VLA
  行为有差异）。M0 用到的 `_Alignas`、`_Static_assert`、`stdatomic.h`
  在 clang 下全部可用且行为正确。
* 诊断信息质量明显好于 MSVC，对"类型宽度不一致""隐式提升"这类问题的
  提示更准确。
* 直接复用 MSVC 的 CRT 与 Windows SDK，所以后续调 Win32 API 时不存在
  兼容问题（MinGW 的 TDM-GCC 4.9.2 太老，头文件落后，不适合）。

**踩过的坑**：`clang --target=x86_64-w64-windows-gnu` 走 MinGW 路径会链接失败
（`unable to find library -lgcc_eh`），因为 TDM-GCC 的库布局和 clang 期望的
不一致。所以不要试图用 clang + MinGW 组合，老老实实用 MSVC 目标。

### 1.2 `CMAKE_C_EXTENSIONS OFF`

传 `-std=c11` 而不是 `-std=gnu11`。目的是把"不小心用了 GNU 扩展"变成编译期
错误，而不是等到换编译器（比如 MSVC）时才发现。代价是不能用 `typeof`、
语句表达式等便利特性 —— 这个代价是值得付的。

### 1.3 `-Wdouble-promotion` 是数学库的头号护栏

`float` 被隐式提升为 `double` 运算再截回 `float`，慢一倍以上，而且看起来
完全正常。这个告警把问题变成编译期可见。配套约定：所有 libm 调用必须用
`f` 后缀版本（`sqrtf` / `cosf` / `fabsf`）。

### 1.4 `tools/env.sh` 里的路径必须先转成 POSIX 风格

**坑**：往 `PATH` 里塞 Windows 风格路径 `D:/Program Files/...`，会被
MSYS/Git Bash 的路径列表转换逻辑**从冒号处截断**成两段 `D` 和
`/Program Files/...`。现象是"目录明明存在，但 `command -v ninja` 找不到"，
而且不会有任何报错。

所以 `env.sh` 里有一个 `_myengine_to_posix` 把 `D:/foo` 转成 `/d/foo`。
`env.cmd` 用 Windows 风格，两者互不影响。

### 1.5 源文件显式列出，不用 `file(GLOB)`

代价是新增文件要改 CMakeLists 一行；收益是"构建系统里的东西永远等于仓库里
的东西"，不会因为 GLOB 的缓存行为出现"本地能编、CI 编不过"。

## 二、类型与句柄

### 2.1 固定宽度别名，禁止裸 `int`/`long`

序列化格式、GPU 布局、句柄位域都依赖确定的宽度。`long` 在 Windows 是 4 字节、
Linux 是 8 字节，一旦漏用一次就是跨平台移植时的定时炸弹。

### 2.2 `handle_t` 是 32 位打包值，不是指针

```
 31            24 23                          0
 +---------------+-----------------------------+
 |  generation   |           index             |
 +---------------+-----------------------------+
```

* `index` 是槽位下标，**0 号槽永久保留**，因此 `handle_make(0, 0) == HANDLE_INVALID`
  天然成立，校验时不需要特判"索引 0 且代际 0"这种组合。
* `generation` 在槽位释放时自增，使旧句柄立刻失效。

**代价**：8 位代际意味着同一槽位复用 255 次后回绕，理论上存在 ABA 风险。
换成 `{u32 index, u32 generation}` 的 8 字节句柄可以消除，但所有句柄容器
翻倍。M0 选择 4 字节；如果将来出现"长时间运行后偶发的句柄误用"，第一件事
就是查这里。

**验证**：`tests/test_memory.c` 里的 `pool_generation_wraps_without_breaking`
故意复用同一个槽位 600 次，确保回绕后代际仍与句柄一致。

### 2.3 `pool_slot_t::generation` 必须是 `u8`

**坑**：如果槽位里的代际存成 `u32`（会一直增长到几千），而句柄里只有 8 位，
那么 `pool_get` 里 `slot->generation != handle_generation(h)` 永远为真，
**所有句柄都会被判定为失效**。这是个非常隐蔽的坑，所以槽位里也用 `u8`，
并在回绕时跳过 0。

## 三、内存

### 3.1 `allocator_t::free` 带 `size` 参数

标准 `free` 只给指针。我们额外要求传 size，理由：

* 追踪分配器靠它统计存活字节数，否则必须在每次分配前塞一个尺寸头，
  而尺寸头会**破坏调用方要求的对齐**。
* arena / pool 这类"分配器自己就是内存来源"的实现，`free` 是空操作，
  但仍需要知道字节数来更新统计。
* 代价是调用方必须记住申请了多大 —— 引擎内部所有调用点天然知道。

### 3.2 为什么要有追踪分配器

"无泄漏"如果只是口号，就永远只是口号。`allocator_tracking_t` 让每个测试
都能在结束时断言 `live_blocks == 0`，把这条质量目标变成**可执行断言**。
它同时也是将来运行期内存面板的数据源。

注意：`base` 必须是结构体第一个成员，才能安全地 `(allocator_tracking_t *)self`。

### 3.3 Arena 的分配粒度统一取 16 字节

所有分配都按 16 字节向上取整，使 `block->used` 始终是 16 的倍数，
16 字节对齐的分配不需要任何额外填充。

代价：大量小对象会有最多 15 字节的浪费（1 万个 12 字节对象 → 160KB 而非
120KB）。收益是分配路径上没有分支、没有对齐计算，且行为可预测。
对帧 arena 这种"装的是中等大小块"的场景是划算的。

### 3.4 Arena 的对齐必须基于绝对地址（重要）

**坑**：块头是 16 字节对齐的，所以块内数据区起点 `base` 只保证 16 字节对齐。
如果写成

```c
usize offset = ENGINE_ALIGN_UP(block->used, alignment);   // 错
```

那么当 `alignment = 256` 时，算出来的是"相对 `base` 对齐"的偏移，
而 `base` 本身可能不是 256 对齐的，最终指针的绝对地址就不对齐。

正确写法：

```c
const uintptr_t address = (uintptr_t)base + (uintptr_t)block->used;
const usize offset = (usize)(ENGINE_ALIGN_UP(address, alignment) - (uintptr_t)base);
```

这种 bug 在只用 16 字节对齐时**完全看不出来**，等 M2 之后上 SIMD
（`movaps` 要求 16 字节对齐、AVX 要求 32）才会以"随机崩溃"的形式暴露。

### 3.5 `arena_mark` / `arena_rewind` 会真的释放后续块

只回退游标是不够的：一次"分配 1GB 后失败"会让那 1GB 永久挂在 arena 上。
所以 `rewind` 会遍历并释放 mark 之后新建的所有块。

### 3.6 Pool 用显式 `in_use` 而不是 `next_free == POOL_NIL`（重要）

**坑**：最初的实现用一个值 `POOL_NIL` 同时表示两件事 —— "槽位被占用"和
"空闲链表结束"。这导致**链表尾部的那个空闲槽被误判成"正在使用"**，
迭代器会多遍历一个元素（测试里表现为 `visited == 6` 而期望 5）。

修法：加一个显式的 `u8 in_use` 字段。结构体从
`{u8, pad×3, u32}` 变成 `{u8, u8, pad×2, u32}`，**大小不变**（8 字节），
对齐填充正好用上。

### 3.7 Pool 容量固定，不做扩容

扩容会移动 `data` 指针，使所有已发放的裸指针失效。需要更多槽位就在初始化
时给够。池满时 `pool_alloc` 返回 `HANDLE_INVALID`，不扩容、不崩溃。

### 3.8 `pool_alloc` 返回的内存会被清零

新对象看到上一个对象的残留数据，会表现为"随机出现的幽灵字段"。
确定性比省这点 `memset` 重要得多。

### 3.9 线程模型：arena 与 pool 都**不是**线程安全的，且刻意不加锁

正确用法是"一个线程一个 arena"（主线程帧 arena、加载线程加载 arena）。
跨线程共享请由上层加锁或改用每线程独立实例。
加锁会把"分配"这个最热的操作变成有竞争的路径，得不偿失。

## 四、容器

### 4.1 动态数组叫 `array` 而不是 `vec`

原始需求里这个模块叫 `vec`，但它与数学库的 `vec2/vec3/vec4` 撞名。
一个项目里出现 `vec` 和 `vec3` 两种完全不同的东西，读代码的人迟早会看错。
改名为 `array`，数学库保留 `vec*` 前缀。

### 4.2 数组是运行时泛型 + 调用点类型转换

容器本体是"字节数组 + 元素大小"（一份实现，代码量小、好测），
元素访问通过 `ARRAY_PUSH` / `ARRAY_AT` / `ARRAY_FOREACH` 宏在调用点做类型转换。
这是 C 里在"零重复代码"和"类型安全"之间的常规折中。

放弃的方案：用宏生成类型化数组（`ARRAY_TYPEDEF(int, IntArray)`）。
类型更安全，但每个类型一份代码，调试器里符号爆炸，且宏里的多语句
`do{}while(0)` 极易写错。

### 4.3 哈希表只做 `u64 -> u64`

引擎里 90% 的哈希需求是"句柄 → 槽位"、"字符串哈希 → ID"、"ID → 索引"
这类整数映射。把这一种做扎实、做快、做对，比一开始就上泛型宏生成器更有价值。
需要结构体值时，把值编码成句柄或索引即可。

### 4.4 哈希表用后移删除，不用墓碑

墓碑方案的问题：删除会在表里留下"坑"，随删除次数增加探测链越来越长，
而且迭代要跳过墓碑、查询要把墓碑当作"继续找"的信号，三处逻辑都要小心。
后移删除让表在删除后依然保持"无空洞"，查询、插入、迭代三处逻辑都能保持
最简单的形式。

**踩过的坑（严重）**：后移删除有两个游标，**必须独立前进**：

* `j` 是扫描游标，每轮**无条件前进**；
* `i` 是当前空洞位置，**只在真的搬移了元素时才跟着 `j` 走**。

最初写成 `j = (i + 1) & mask`（从 `i` 重新推导），那么当某个元素不该被搬移时
`j` 就不会前进，循环卡在原地。现象是**删除操作直接挂死**（不是返回错误，
是死循环）。这个 bug 是靠随机对拍测试跑出来的。

判据：元素在 `j`，理想槽位是 `home`。若从 `home` 出发到 `i` 的距离**小于**
到 `j` 的距离，说明 `i` 位于它的探测路径上，搬过去不会破坏任何查询。

### 4.5 哈希表用独立的 `states` 数组区分"空"与"键为 0"

否则必须占用某个键值做哨兵，而"某个键不能存"这种限制会在很久以后变成
一个莫名其妙的 bug。

### 4.6 哈希函数用 splitmix64 收尾混合

不用"乘一个大质数"这种简单方案：那样低位分布很差，而线性探测正好是用低位
决定初始槽位（`& mask`），低位差会直接变成严重聚集、性能塌陷。
`tests/test_hash.c` 里有低位分布的粗测和雪崩性测试。

## 五、数学库

### 5.1 为什么是 header-only（有意偏离"接口/实现分离"）

向量运算每条只有几条指令，函数调用开销占比极高。只有放在头文件里、
让编译器看到调用点上下文，才能真正内联并向量化。分离到 `.c` 会强制走 ABI，
在 Win64 上 16 字节结构体还会走隐藏指针返回，单次 `vec3_add` 的代价可能
比实际运算高一个数量级。

只有两个函数例外地放在 `math.c`：`math_next_pow2_u32`（位运算循环）和
`math_set_flush_denormals`（修改硬件浮点状态）。

### 5.2 内存布局与 `_Alignas` 的坑（重要）

```
vec2_t   8 字节,  4 字节对齐
vec3_t  16 字节, 16 字节对齐   ← x, y, z 之后有一个 pad
vec4_t  16 字节, 16 字节对齐
quat_t  16 字节, 16 字节对齐
mat3_t  48 字节, 16 字节对齐   ← 3 列 × vec3_t(16)
mat4_t  64 字节, 16 字节对齐   ← 4 列 × vec4_t(16)
```

**坑**：`_Alignas` 作用于该声明里的**每一个** declarator。所以

```c
typedef struct { _Alignas(16) float x, y, z, w; } vec3_t;   // sizeof == 64 !
```

是错的 —— 等于给 x/y/z/w 各自加了 16 字节对齐。正确写法是只让第一个成员带
`_Alignas`，其余成员另起一条声明：

```c
typedef struct { _Alignas(16) float x; float y; float z; float pad; } vec3_t;
```

所有布局都用 `_Static_assert` 钉死，改错会立刻编译失败。

### 5.3 `vec3_t` 的 16 字节是权衡后的选择

收益：16 字节对齐后可以整块装进 SSE 寄存器，将来做 SIMD 不需要改数据布局
（改布局是最贵的部分）。

代价：`vec3` 数组浪费 25% 内存，且 `pad` 字段容易让人困惑。

**约定**：顶点缓冲**不要**用 `vec3_t`，GPU 侧用紧凑的 12 字节布局
（M2 会引入专门的 vertex 类型）。`pad` 字段命名为 `pad` 而不是 `w`，
就是为了防止有人"顺手"把它当齐次坐标用。

### 5.4 `mat3_t` 是 48 字节而不是 36

每列是一个 `vec3_t`（16 字节含填充）。多出的 12 字节换来 16 字节对齐和
与 `vec4_t` 统一的内存布局。法线矩阵、旋转、缩放用得上，且数量远少于 `mat4`，
空间开销可接受。

### 5.5 坐标系与投影约定（全引擎唯一权威定义）

| 项 | 约定 |
|---|---|
| 世界空间 | 右手系，Y 轴向上 |
| 相机 | 默认看向 **-Z**（与 OpenGL 传统一致） |
| 裁剪空间 | X/Y ∈ [-1, 1]，**Z ∈ [0, 1]** |
| NDC 深度 | [0, 1]，近平面 = 0，远平面 = 1 |
| 矩阵存储 | **列主序**（`col[c]` 是第 c 列） |
| 乘法语义 | `mat4_mul(a, b)` = a·b；`(a·b)·v == a·(b·v)`，即**先 b 后 a** |

**为什么深度取 `[0,1]`**：Vulkan 与 D3D 原生就是 `[0,1]`，只有 OpenGL 默认
`[-1,1]`。如果按 GL 的 `[-1,1]` 设计，等 M13 接 Vulkan 时要么改所有投影矩阵、
要么在每个后端插一层修正矩阵，两边的调试成本都很高。反过来，GL 4.5 提供
`glClipControl(GL_LOWER_LEFT, GL_ZERO_TO_ONE)` 可以一次性对齐到 `[0,1]`。

**原则：按 Vulkan 语义设计，让 GL 去适配。**

**为什么列主序**：与 GLSL 的 `mat4` 内存布局一致，上传 GPU 无需转置。
代价是手写代码时 `M[row][col]` 的直觉需要反过来，所以 `mat.h` 里提供了
`mat4_from_rows()` 按行优先书写顺序构造，调用处可以直接照抄教科书矩阵。

### 5.6 `mat3/mat4_transpose` 曾经是空操作（重要）

**坑**：列主序下 `transpose` 的实现如果误用 `from_rows` 再传一遍同样的元素：

```c
// 错：等价于原地转置两次 → 返回原矩阵
return mat4_from_rows(m.col[0].x, m.col[1].x, m.col[2].x, m.col[3].x, ...);
```

正确写法必须用 `from_columns`：

```c
return mat4_from_columns(vec4_make(m.col[0].x, m.col[1].x, m.col[2].x, m.col[3].x), ...);
```

**为什么难发现**：旋转矩阵、缩放矩阵、对角矩阵的转置都等于自身。
`mat4_normal_matrix` 用的 `transpose(inverse(M))`，在均匀缩放下也和
`inverse(M)` 相等。所以只要测试里全是这类矩阵，**所有断言都会通过**。

**结论**：转置必须用**非对称矩阵**做测试。现在
`tests/test_mat.c::transpose_and_determinant` 专门检查
`transpose(M).col[0].y == M[0][1]`。

### 5.7 `mat4_look_at` 曾经少转置一次（重要）

视图矩阵 = 相机变换的逆。相机到世界的旋转 `R`，其列是相机的三个基向量
（右 `s`、上 `u`、后 `-f`）；逆变换的旋转部分是 `R^T`，行依次是 `s`、`u`、`-f`。
列主序存储时：

```
col0 = ( s.x,  u.x, -f.x, 0)
col1 = ( s.y,  u.y, -f.y, 0)
col2 = ( s.z,  u.z, -f.z, 0)
col3 = (-dot(s,eye), -dot(u,eye), dot(f,eye), 1)
```

**坑**：最初按 `col0 = (s.x, s.y, s.z)` 写，存进去的其实是 `R` 而不是 `R^T`。
当相机恰好沿坐标轴看向原点时 `R` 是对称的，测试照样全过；只有相机带斜角时
才暴露，表现为"整个世界被斜着拧了一下"。

现在测试里专门用了一台斜视角相机（`eye = (-4, 1, 7)`），
并对变换前后的**距离**做不变量检查（刚体变换必须保距）。

### 5.8 四元数的约定

* 存储顺序 `{x, y, z, w}`，`w` 是标量部分。与 `vec4_t` 字段顺序一致。
* `quat_mul(a, b)` = a·b，**表示"先应用 b，再应用 a"**。
  要"先绕 X 转 30 度，再绕 Y 转 45 度"，写的是
  `quat_mul(quat_rotation_y(y), quat_rotation_x(x))`。顺序写反不会报错，
  只会让物体朝一个"看起来差不多但就是不对"的方向。
* `quat_from_euler(x, y, z)` = `qz * qy * qx`，即按 X → Y → Z 依次绕
  **固定世界轴**旋转。
* `q` 与 `-q` 表示同一旋转，因此 `quat_near` 同时接受取负的情况，
  而 `quat_equal` 不接受。
* `quat_rotate_vec3` **要求单位四元数**。展开式只在 `|q| = 1` 时才等价于
  `q·v·q*`；传入非单位四元数不会报错，只会让结果既被旋转又被缩放。
  Debug 下有断言拦住。
* `quat_inverse` 返回数学意义上的逆 `q*/|q|²`，**对非单位四元数结果也不是
  单位四元数**（模长为 `1/|q|`）。

### 5.9 `quat_from_mat3` 用 Shepperd 方法分四种情况

直接解 `w = sqrt(1+trace)/2` 在 `trace` 接近 `-1` 时，会因为开根号下出现
负数而失去精度甚至产生 NaN。Shepperd 方法总是挑对角线上最大的那个分量
开根，保证被除数不会接近 0。

测试里覆盖了四个分支：`trace > 0`，以及三个对角分量各自最大的情况。
只测一个普通旋转的话，另外三个分支可能藏着 bug 却永远不会被触发。

### 5.10 `math_wrap_angle` 的边界不能用精确比较

**坑**：最初实现是 `math_wrap(v, -PI, PI)` 之后加一句
`if (r == -F32_PI) r = F32_PI;`。但 `-3*F32_PI` 在 float 下无法精确表示，
`fmodf` 会返回与 `-PI` 相差约 1e-7 的值，精确比较失效，
结果会随机停在 `-PI` 侧或 `+PI` 侧。

改成"先折到 `[0, TAU)` 再折到 `(-PI, PI]`"，全程只有一次比较，边界行为确定。

对应地，测试里对 `±3π` 验证的是**绝对值等于 π**（`+π` 与 `-π` 表示同一个
角度），而不是要求某个具体的代表值 —— 后者是过强的断言。

### 5.11 `math_set_flush_denormals` 做成显式开关，不自动开

打开 FTZ/DAZ 会让非规格化数被清零，这**会改变浮点运算结果**。
单元测试里如果拿极小值做近似比较，会因为结果被清零而失败。
所以由引擎初始化时按构建类型决定是否打开，而不是在 `math_init` 里自动开。

另外注意：MXCSR 是**每线程独立**的，所以本函数必须由每个线程自己调用一次。

### 5.12 只支持 64 位目标

`_Static_assert(sizeof(void *) == 8)` 直接把 32 位目标拦在编译期。
32 位下 `handle_t` 的打包策略、指针比较、SIMD 对齐都需要重新设计，
与其静默跑错不如直接拦住。

## 六、日志与断言

### 6.1 日志是"线程安全单例"（有意例外）

日志在语义上就是进程级设施。强行把它实例化并逐层传递，只会污染每一个
函数签名（`render_draw(engine, ctx, logger, ...)`）。所以接受它作为
"无全局状态"约束的例外，断言同理。

### 6.2 未调用 `log_init` 也能用

默认只输出到控制台、级别 `INFO`。这样"启动早期就崩了"的场景仍然有日志
可看 —— 否则会变成盲查。

### 6.3 线程安全用 C11 `atomic_bool` 自旋锁，不用 `atomic_flag`

`atomic_flag` 必须用 `ATOMIC_FLAG_INIT` 初始化，而它在"静态结构体的成员"
位置上各编译器的支持程度不一致。`atomic_bool` 零初始化即为 `false`，
用 `exchange` 循环实现自旋，行为确定。

`TODO(M1)`：改用 PAL 提供的互斥量。自旋锁在"另一个线程正在写磁盘"时会空转
烧 CPU，日志量大时这是可见的浪费。

### 6.4 只在 WARN 以上立即刷盘，且只在 WARN 以上输出 `file:line`

* 正常日志每行 `fflush` 会让日志本身成为瓶颈，但警告与错误必须保证
  "程序崩了也能在文件里看到"。
* `file:line` 只在 WARN 以上输出：TRACE/DEBUG/INFO 是"运行过程"，读者关心
  消息本身；WARN/ERROR 是需要去改代码的，这时候能直接跳到出错位置就很值。

### 6.5 超长日志显式标记截断

单行缓冲 4KB，超出部分不会静默丢弃，而是写上 `...<截断>`。
静默截断会让日志"看起来正常"但信息不完整，比报错更难发现。

### 6.6 `ASSERT_MSG` 需要单独的变参函数

**坑**：宏里没法把 `__VA_ARGS__` 拆成"格式串 + 参数"两段。最初的实现用
`"" __VA_ARGS__` 做字符串拼接，只支持单个字面量消息，一旦带参数就会
变成"参数太多"的编译错误。正确做法是提供一个变参函数：

```c
void engine_assert_fail_fmt(const char *expr, const char *file, int line,
                            const char *func, const char *fmt, ...);
```

### 6.7 `ENGINE_DEBUG` 由 CMake 注入，不依赖 `NDEBUG`

标准 `assert` 的开关由 `NDEBUG` 控制，而 `NDEBUG` 会被第三方库的构建脚本
意外定义/取消定义，导致"Debug 构建里断言被关掉"这种极难排查的问题。
这里由 CMake 按构建类型显式注入 `ENGINE_DEBUG`。

### 6.8 `VERIFY` 与 `ASSERT` 的区别

* `ASSERT(expr)`：Release 下整个表达式被编译掉，**expr 不求值**。
* `VERIFY(expr)`：Release 下仍求值，只是不检查结果。
  用于"表达式本身有副作用且必须执行"的场合。

## 七、测试框架

### 7.1 自己写，不用 Unity / CMocka

* 依赖越少，"换编译器/换平台时测试先崩"的概率越低。本框架只用 C11 标准库。
* 需要的功能其实很少：注册、断言、筛选、计时、彩色输出。加起来 200 行。
* 断言宏需要知道 `vec3`/`mat4` 这类自定义类型才能打印有意义的失败信息，
  用第三方框架反而要写一堆 adapter。

### 7.2 显式注册，不做自动注册（链接器段技巧）

那类方案依赖具体工具链，换编译器就**静默失效**（测试不再运行，但看起来
"全过"）。显式注册虽然多写一行，但少一次"测试根本没跑"的灾难。

新增测试文件的清单在 `tests/test_suites.h`，这个文件要当**清单**看：
忘了加一行不会报错，只会变成测试没跑。

### 7.3 用"随机对拍"覆盖组合边界

手写用例很难穷举出所有删除顺序。`randomized_matches_naive_reference`
用一个朴素的"数组线性查找"作为参考实现，随机做插入/删除/查询并逐步对拍。
哈希表那个死循环 bug 就是靠这个测试跑出来的。

## 八、M0 遗留问题 / 已知代价

| 项 | 现状 | 计划 |
|---|---|---|
| 代际 8 位会回绕 | 同槽复用 255 次后理论上 ABA | 出现相关问题再换 8 字节句柄 |
| 日志自旋锁 | 磁盘 IO 时会空转烧 CPU | M1 换成 PAL 互斥量 |
| `console.c` 在 core 下 | 是纯平台代码 | M1 迁到 `src/platform/win32/` |
| 数学库未用 SIMD | 标量实现，仅保证对齐 | M2/M4 性能阶段再上 SSE/AVX |
| `vec3_t` 25% 内存浪费 | 换取对齐 | 顶点数据用单独的紧凑类型（M2） |
| pool 不支持扩容 | 容量固定 | 有意为之，见 3.7 |
| 渲染层尚无抽象 | M0 不含渲染 | M2 按 Vulkan 语义设计接口 |

## 九、给后续阶段的提醒

1. **M2 的 `render_backend_t` 必须按 Vulkan 语义设计**（显式 render pass、
   显式资源布局、不可变 pipeline state object、显式同步），GL 实现内部做
   状态机降级适配。如果按 GL 的直觉设计，M13 会变成重写渲染层。
2. **M4 结束时就用一个极简 demo 在 GL + D3D11 各跑一次**，把多后端风险
   从 M13 前置到 M4。
3. **热重载机制要在 M7 之前设计好**（独立的分配区 + 资源双缓冲槽），
   否则 M7 会被迫打破"帧内零 malloc"的约束。
4. **"10 万精灵 60FPS" 的前提条件要写死**：同一纹理图集 + per-instance
   压缩（传 `vec4(pos.xy, scale, rot)` + `vec4(uv)` + `u32 color`，
   不要传 mat4）+ 动态 VBO orphan。验收标准应改为"同一图集内 10 万精灵 <16ms"。
5. **冷启动 <1s 会被 GL 首次 shader 编译吃掉几百 ms**，需要预编译二进制
   （GL 用 `glProgramBinary` + SPIR-V，D3D 用 FXC 离线编译）。
