# M2 设计决策记录

> 记录 M2 阶段所有"为什么这么做"以及踩过的坑。
> 改 M2 的代码前先读这里；改动后如果推翻了某条决策，请把这一条也一起改掉。

## 一、后端抽象接口（本阶段最重要的产出）

### 1.1 核心约束：接口里不允许出现任何图形 API 类型

`render_types.h` / `render_backend.h` 里**不许出现** `GLuint` / `GLenum` /
`VkImage` / `ID3D11Texture2D`，也不许出现 `GL_RGBA8` / `VK_FORMAT_*` 这类
具体枚举值。

**为什么这条值得反复强调**：一旦接口里漏出一个 GL 类型，M13 接 D3D/Vulkan 时
就必须改接口 —— 而接口一改，所有调用点、所有材质、所有资源管理代码都要跟着改。
那不是"加一个后端"，那是重写渲染层。

M2 结束时验证方式：在 `examples/02_render/main.c` 里搜 `gl->`，搜不到。

### 1.2 状态是"打包成 desc 一次性提交"，不是"逐项设置"

OpenGL 的习惯是：

```c
backend_set_blend(true);
backend_set_blend_func(SRC_ALPHA, ONE_MINUS_SRC_ALPHA);
backend_set_depth_test(true);
backend_set_cull(BACK);
backend_draw();
```

这套在 Vulkan 上**完全无法实现**：Vulkan 的管线状态对象是不可变的，
必须在创建时一次性给定全部状态，运行时只能整块切换。

所以接口收成 `pipeline_desc_t`：一次描述、一次创建、运行时只 `bind_pipeline`。
GL 后端内部把这些状态"摊平"成一组字段 + 一个状态缓存（见 §3）。

### 1.3 保留显式的 render pass

GL 只有"默认帧缓冲"，没有 render pass 这个概念。但接口保留了它：

```c
backend->begin_render_pass(backend, &pass);   // 设置视口/裁剪/清屏
... draw ...
backend->end_render_pass(backend);
```

理由：M4 引入离屏渲染、M6 引入"3D 渲染到纹理"时，调用方**不需要改**。
GL 后端在 `begin_render_pass` 里做的就是"设置视口 + 清屏"，
但调用方看到的语义与 Vulkan 一致。

### 1.4 uniform 是"块 + 绑定点"，不是"按名字"

GL 允许 `glGetUniformLocation` + `glUniformMatrix4fv` 按名字设 uniform。
**Vulkan 没有这个概念**：它只有"把一块内存绑定到某个 descriptor 槽位"。

如果接口做成按名字设 uniform：
* 每个后端都要实现一套 GLSL/SPIR-V 反射；
* 每次 draw 前的 uniform 上传会变成十几次 API 调用，在 Vulkan 上这些调用
  要写进命令缓冲，开销完全不可接受。

所以采用 **uniform 块 + std140 布局**（见 §2）。

### 1.5 顶点布局是"binding 数组 + attribute 数组"

GL 用 `glVertexAttribPointer` 逐个描述属性；Vulkan 用
`VkVertexInputBindingDescription[]` + `VkVertexInputAttributeDescription[]`。

接口用后者。这种分离让"交错顶点缓冲"和"分离顶点缓冲"能用同一套描述表达，
也为 M3 的实例化数据（`per_instance` binding）留好了位置。

### 1.6 属性 location = 语义枚举值

```c
#define RENDER_ATTRIBUTE_LOCATION(semantic) ((u32)(semantic))
```

POSITION=0、NORMAL=1、TANGENT=2、TEXCOORD0=4、COLOR0=6……

这样"顶点布局描述"与"着色器里的 `layout(location = N)`"不用再维护一张对照表 ——
少一张表就少一处会写错的地方。

### 1.7 后端是函数指针表 + `self`

```c
struct render_backend_t {
    const char *name;
    bool (*init)(render_backend_t *self, const render_backend_desc_t *desc);
    ...
};
```

实现方的结构体必须把 `render_backend_t` 作为**第一个成员**，
这样回调里可以安全地 `(concrete_t *)self` 转换。这是 C 里实现多态的常规做法。

---

### 1.8 一条**没做到**的约束：显式资源布局与显式同步

计划的原文是"后端接口按 Vulkan 语义设计：**显式资源布局**、显式同步"，
并且"每一项都要能解释为什么对 Vulkan 也成立"。

现状必须如实写：

| 那一版要求的东西 | 接口里有没有 |
| --- | --- |
| 显式 render pass（load/store 操作、附件列表） | ✅ `begin_render_pass` + `render_pass_desc_t`（见 1.3） |
| 显式 pipeline 状态打包 | ✅ `pipeline_desc_t`（见 1.2） |
| 显式 uniform 绑定点 | ✅ 块 + binding（见 1.4） |
| **显式资源内存布局**（描述集 / 绑定布局对象） | ❌ 没有。纹理与缓冲的"布局"信息藏在各后端自己手里 |
| **显式同步**（barrier / fence / semaphore 的任何形式） | ❌ 没有。全仓库 grep `layout`/`barrier`/`fence`/`semaphore` 在 `include/engine/render/` 与 `src/render/` 零命中 |

也就是说：接口"接近 Vulkan 的形状"这条做到了，
但"显式布局 + 显式同步"这半句只做到了 render pass 这一层。

为什么当时没做，以及这条账什么时候结：OpenGL 的等价物是隐式的
（驱动自己推断纹理布局转换、自己决定何时同步），
要在 M2 造出 barrier API，只能造一个**在 GL 后端里空转**的 API ——
它既不能被验证（没有第二个后端可比），又会给人"同步已经显式了"的错觉。
所以现在记成欠账而不是假装做完了。

真正会撞上它的时间点是 **M13（D3D11/Vulkan 后端）**：
Vulkan 需要 `VkPipelineLayout` + descriptor set 与 image layout 转换，
D3D11 需要 root signature 与显式的 map/unmap 或 resource transition，
那时候这套接口要么现在就把形状定对，要么到时候重画一半。
**建议**：M13 开工前先做一个只有接口、没有实现的最小验证（用第二个后端骨架填一遍），
再决定接口怎么改 —— 这比在 M2 凭想象补 API 便宜。

## 二、uniform 块与 std140

### 2.1 C 结构体与 GLSL 声明放在同一个文件

`uniforms.h` 里既有 C 结构体，也有对应的 GLSL 声明字符串：

```c
typedef struct frame_uniforms_t { mat4_t view; mat4_t projection; ... } frame_uniforms_t;
#define RENDER_UNIFORM_BLOCK_GLSL \
    "layout(std140, binding = 0) uniform FrameUniforms { mat4 u_view; ... };\n"
```

**理由**：std140 的布局规则很细（mat4 按 4 个 vec4 对齐、结构体大小要对齐到 16）。
如果两边分处两个文件，某天有人给 C 结构体加一个字段、忘了改 GLSL，
症状是"某个 uniform 莫名其妙变成 0"—— 极难定位。

放在一起 + 一堆 `_Static_assert`，能把这类错误变成编译期失败。

### 2.2 GL 后端用**真正的 UBO**，不用 `glUniform*`

`glBindBufferBase(GL_UNIFORM_BUFFER, binding, buffer)` + `glBufferSubData`。

着色器里用 `layout(std140, binding = N)` 直接指定绑定点，
不需要 `glGetUniformBlockIndex` / `glUniformBlockBinding`。

这么做是**故意让 GL 走和 Vulkan 一样的路径**。如果用 `glUniform*`，
GL 上能跑、Vulkan 上跑不了，抽象就漏了。

### 2.3 每帧只有 2 次 uniform 上传

* `RENDER_UNIFORM_BINDING_FRAME`：一次上传，本帧所有 draw 共用
  （view / projection / view_projection / 相机位置 / 光照）
* `RENDER_UNIFORM_BINDING_OBJECT`：每个 draw 上传一次
  （model / normal_matrix / tint）

对比"每个 uniform 一次 glUniform 调用"，一次 1000 物体的场景能省掉上万次 API 调用。

### 2.4 `normal_matrix` 用 mat4 而不是 mat3

std140 下 mat3 会被当成 3 个 vec4（48 字节），C 侧的 `mat3_t` 也是 48 字节，
本来能对上。但用 mat4 让着色器里的写法更统一
（`mat3(u_normal_matrix)` 取左上 3x3），多出来的 16 字节在每对象数据里可以忽略。

### 2.5 sRGB 的决定

* 颜色纹理（albedo / UI）用 `PIXEL_FORMAT_*_SRGB` 上传，硬件自动解码成线性；
* 数据纹理（法线、粗糙度、遮罩）用 `_UNORM`，数值原样使用。

传错的后果：颜色纹理传 UNORM 会显得发灰发暗；法线贴图传 SRGB 会让光照方向错。
所以 `texture_load_*` 都带一个 `srgb` 参数，由调用方按用途决定 ——
加载器**不应该猜**。

### 2.6 默认纹理

1x1 白色 + 1x1 平面法线，在 `gl_backend_init` 里创建。

**没有它们的话**，"忘了绑纹理"会采样到未定义内容，画面出现随机颜色，
而且 GL **不会报任何错**。有了默认纹理，忘记绑定只会得到纯白 —— 一眼能看出问题。

## 三、GL 状态缓存（状态机降级适配）

### 3.1 为什么需要

GL 的状态切换是有成本的（驱动要校验、可能触发管线重编译）。
如果每次 `bind_pipeline` 都把全部状态重设一遍，一个 1000 物体的场景
就是几万次冗余状态调用。

`gl_applied_state_t` 记录"GL 实际处于什么状态"，`bind_pipeline` 时做 diff，
只发真正变化的调用。

### 3.2 帧开始时作废缓存

`begin_frame` 把 `state.valid` 置为 false，下一次 `bind_pipeline` 会全量下发。

理由：外部代码（或调试工具、驱动面板）可能改过 GL 状态。作废的代价只是
下一帧第一次 bind 多几次调用，比"状态缓存与真实状态不一致"这种玄学 bug
便宜得多。

### 3.3 用 `glBlendFuncSeparate` 而不是 `glBlendFunc`

颜色通道与 alpha 通道的因子本来就该能分开设（Vulkan 的
`VkPipelineColorBlendAttachmentState` 也是分开的）。
用 `glBlendFunc` 会把两者绑死，透明叠加时 alpha 通道会算错。

### 3.4 采样器对象

GL 的采样参数存在两个地方：纹理对象上（`glTexParameteri`）和采样器对象上。
用**采样器对象**才能做到"同一张纹理配不同采样方式"（Vulkan 里 sampler 与
image 本来就是分开的对象）。

后端做一个小缓存（16 个槽位，按 `sampler_desc_t` 值比较），避免每次绑定都
创建/销毁。

### 3.5 清屏前要解除写掩码

`begin_render_pass` 里先 `glColorMask(TRUE,TRUE,TRUE,TRUE)` 再 `glClear`，
先 `glDepthMask(TRUE)` 再清深度。

**不这么做的坑**：如果上一次绘制把颜色写掩码设成了"只写红通道"，
直接清屏会得到一个只被清了一半的帧缓冲 —— 这个 bug 极难发现，
因为画面看起来"只是颜色有点怪"。

## 四、句柄的两层结构

```
用户拿到的：  shader_handle_t  ← 由 renderer 的池发放
池槽里存的：  backend 的内部句柄
```

**为什么要两层**：
* 代际校验、资源命名、创建帧号、热重载钩子全部集中在 renderer 一层；
* 后端只需要维护"内部句柄 → API 对象"的映射，职责单一；
* M7 做热重载时，只要遍历 renderer 的池就能找到"所有 shader"，
  不需要后端提供遍历能力。

代价是每次绑定多一次池查找（几次内存访问），可以忽略。

**为什么资源上限宏放在 `render_types.h`**：后端也要用它们开池，
而后端不应该依赖 renderer（依赖方向是 renderer → backend，不能反过来）。

## 五、渲染队列与排序

### 5.1 排序键：layer 在高端，深度在低端

```
 63          32 31                    0
 +--------------+----------------------+
 |    layer     |    quantized depth   |
 +--------------+----------------------+
```

**layer 必须压过深度**。如果深度能压过 layer，一个很远的背景物体
就可能被画到 3D 物体前面。这是"背景永远在最后面"的保证。

### 5.2 深度的方向按 layer 的性质决定

* 不透明层：近 → 远（early-z 能提前丢弃被遮挡的像素）
* 半透明层：远 → 近（混合才有正确结果）

实现上就是半透明层把深度取反（`0xFFFFFFFF - depth_bits`）。

### 5.3 用全序代替稳定排序

`qsort` **不是稳定排序**。同 layer 同深度的两个物体，不同次运行可能排出
不同顺序，表现为"透明物体偶发闪烁"。

解决办法不是实现一个稳定排序，而是让比较函数构成**全序**：
深度相同时再比 `sequence`（插入序号，唯一）。全序下任何正确的排序算法
都会给出唯一结果。

### 5.4 深度量化用 f64 中转

```c
u32 depth_bits = (u32)((f64)t * 4294967295.0);
```

`4294967295` 在 f32 里无法精确表示（会进位到 `4294967296`），
于是 `t == 1.0` 时 `(u32)` 转换的结果是**未定义行为**。
用 f64 中转可以精确表示，转换也就安全。

### 5.5 排序深度用包围盒中心，不用模型矩阵的平移分量

对大网格（例如地形）来说，平移分量可能离物体实际位置很远，
排序结果会明显错误 —— 表现为"地形被画在半透明物体之后"。

`renderer_create_mesh` 时扫描 POSITION 属性算出包围盒并缓存，
之后每帧用 `model × 包围盒中心` 算世界位置。

### 5.6 队列的底层数组不清空内存

`render_queue_begin` 只把 `array_t.size` 归零，保留已分配的内存。
第一帧扩容到峰值后，之后每帧都不再分配 —— 这是"帧内零 malloc"的落点之一。

测试 `queue_reuses_memory_across_frames` 用追踪分配器断言了这一点。

## 六、相机

### 6.1 复用 M0 的矩阵函数，不另写一份

`camera_view_matrix` 内部调 `mat4_look_at`，`camera_projection_matrix` 内部调
`mat4_perspective` / `mat4_ortho`。

**两份实现必然会在某个时刻不一致**，而"投影矩阵对不上"这类问题的表现是
"画面看起来差不多但就是歪了"，排查成本极高。

### 6.2 朝向用四元数

相机的朝向是"一个旋转"，用四元数存不会遇到万向锁，插值（做相机平滑）
也是良定义的。yaw/pitch 只是输入方式，通过 `camera_set_yaw_pitch` 转成四元数。

### 6.3 视锥剔除要单独判 `w <= 0`

```c
if (clip.w <= 0.0f) return false;
```

相机背后的点经过透视除法会得到镜像的结果，落在 `[-1,1]` 里，
**看起来"在视锥内"**。不判掉的话，相机背后的物体会被错误地画出来。

## 七、OBJ 加载

### 7.1 两遍扫描

第一遍只数数量（顶点/法线/UV/面角），第二遍才填数据。

好处是输出数组能一次分配到位，不需要"扩容 + 拷贝"，
而 **arena 没有 realloc** —— 边解析边扩容会浪费大量内存。

### 7.2 索引去重

OBJ 的索引是 `(v, vt, vn)` 三元组。如果按"每个面角一个顶点"直接展开，
一个 1 万面的模型会产生 3 万个顶点，而实际唯一顶点可能只有几千个。

用一个哈希表按三元组去重。键的打包方式：

```c
key = ((v + 1) << 42) | ((vt + 1) << 21) | (vn + 1)
```

每个字段加 1 后占 21 位（0 表示"未指定"，避免与合法的下标 0 冲突）。
上限是 2^21 - 2 个位置/UV/法线，超过会明确报错而不是静默出错。

### 7.3 去重表跑在 arena 上

用 `arena_allocator_t`（M2 新增）把 arena 包装成 `allocator_t`，
让哈希表能跑在 arena 上。

**注意**：这个适配器的 `free` 是空操作（arena 不支持单独释放），
所以只适合"生命周期短、扩容次数有限"的场景。文件解析正好符合。

### 7.4 手写浮点解析，不用 `strtof`

`strtof` / `atoi` 要求输入以 NUL 结尾，而我们的输入是内存块。
直接改内存（写个 NUL 进去）会破坏只读数据。

### 7.5 退化面的语义

`f 1 2` （2 个面角）会被跳过并计入 `skipped_face_count`。
`f 1 2 2`（3 个面角但只有 2 个不同顶点）会被当成一个退化的三角形发出去 ——
零面积三角形由 GPU 自己丢弃，解析器不需要特判。

### 7.6 法线缺失时补默认值

OBJ 允许只有位置没有法线。不补默认值的话，着色器
`normalize(vec3(0,0,0))` 会得到 NaN，表现为**整个模型全黑**。
补成 `(0,1,0)` 至少能看出形状。

## 八、本阶段踩到的坑

### 8.1 `GL_TEXTURE_WRAP_R` 手抄成了 `0x8064`（正确是 `0x8072`）

这是**手写 GL 常量表**的典型风险。值抄错不会编译失败，
只会在运行期由驱动的调试回调报一个 `GL_INVALID_ENUM`。

`gl_types.h` 的文件头里写了"抄错会立刻出错，不会静默"—— 这句是对的，
但"立刻出错"的前提是**开着调试回调**。如果没开 `GL_KHR_debug`，
这个错误只会让采样参数默默失效（wrap_r 保持默认），极难发现。

**结论**：M1 引入的 `glDebugMessageCallback` 在 M2 立刻赚回了成本。

### 8.2 `gl_api_load` 把"失败"也缓存了

`gl_api_load` 原本在函数末尾无条件 `s_loaded = true`。

**症状**：`gl_backend_init` 在创建上下文**之前**调了一次 `gl_api_load()`，
此时没有 current 上下文，`wglGetProcAddress` 全部返回 NULL，
于是整张残缺的表被永久缓存下来。之后即使上下文就绪，也再拿不到函数指针 ——
报"49 个必需函数加载失败"，看起来像驱动问题。

**修法**（两处都要改）：
* `gl_api_load` 失败时**不缓存**，允许后续重试；
* `gl_backend_init` 把 `gl_api_load()` 移到 `gl_context_create` 之后。

### 8.3 `vertex_format_byte_size` 对紧凑格式算错

原本写成"分量数 × 4"，于是 `UNORM8X4` 算成 16、`UNORM16X4` 算成 16。
实际应该是 4 和 8。

**后果**：顶点布局校验通过（因为校验用的是同一个错值），
但实际数据错位，画面一片混乱。测试里只覆盖 float 格式的话完全发现不了。

现在测试把每种"分量宽度"都覆盖了。

### 8.4 `camera_view_depth` 多了一个负号

原本写成 `return -vec3_dot(to_point, camera_forward(camera));`。

相机看向 -Z，前方点的 `to_point.z < 0`，`forward = (0,0,-1)`，
点积本身已经是正值 —— 再加负号就全反了。

**后果**：排序深度全部反号，不透明层变成"从远到近"绘制。
画面**看起来正常**（不透明物体谁先画都对），但 early-z 完全失效，
而且半透明的顺序也错了。这是"不崩、不报错、只是变慢 + 偶尔不对"的典型。

### 8.5 `arena_allocator_t` 定义在 `arena_t` 之前

头文件里的类型顺序错了，编译直接失败（`unknown type name 'arena_t'`）。
这类错误至少是"立刻可见"的，属于好消息。

### 8.6 C 里不能对函数返回的结构体取地址

```c
renderer_create_shader(renderer, &(shader_desc_t)shader_builtin_lit_textured());  // 错
```

`shader_builtin_lit_textured()` 返回的是右值，不能取地址；
`(shader_desc_t)` 这种"转换成同一类型"的写法在 `-Wpedantic` 下也不合法。

正确做法是先存成局部变量：

```c
const shader_desc_t desc = shader_builtin_lit_textured();
renderer_create_shader(renderer, &desc);
```

### 8.7 `renderer_t` 必须是不透明类型

最初把 `renderer_t` 定义在 `renderer.c` 里，同时提供
`renderer_init(renderer_t *, ...)` —— 调用方无法在栈上声明这个类型。

改成 `renderer_create()` / `renderer_destroy()` 返回/接受指针，
和 `platform_window_t` 保持一致。内部结构（资源池、帧 arena、渲染队列）
是实现细节，暴露出去只会诱导外部代码直接改它的字段。

### 8.8 第三方单头库的告警要单独关

stb_image 用 `-Wall -Wextra -Wpedantic` 编译会产生几十条它自己风格的告警。
为了它把整个引擎的告警标准放宽是本末倒置。

用 `set_source_files_properties(... COMPILE_OPTIONS "-w")` 单独关掉这一个文件。
注意 `COMPILE_OPTIONS` 是**追加**到目标选项之后的，所以 `-w` 会覆盖前面的 `-Wall`。

### 8.9 `goto cleanup` 跳过的变量未初始化（M1 就踩过，M2 又踩了一次）

clang 报 `-Wsometimes-uninitialized`。所有会被 `cleanup` 用到的变量
必须声明在第一个 `goto` 之前并初始化。

## 九、M2 遗留问题 / 已知代价

| 项 | 现状 | 计划 |
|---|---|---|
| 资源池定容 | shader 64 / texture 512 / mesh 1024 / pipeline 256 | M7 的资源层改成可增长 |
| 无渲染目标抽象 | 只支持默认帧缓冲 | M4 加 `render_target_t` + 离屏渲染 |
| 无实例化渲染 | 后端接口支持（`per_instance` binding + `draw_instanced`），但 renderer 还没暴露 | M3 的精灵批渲染 |
| 光照只有单平行光 | Lambert + 环境光 | M4 换成 PBR |
| OBJ 扇形三角化只对凸多边形正确 | 凹多边形会出错 | M7 或按需再改 |
| 采样器缓存只有 16 个槽位 | 轮转覆盖 | 够用；真不够时改成动态 |
| 材质是值类型 | 每次提交复制一份 | 有意为之，见 material.h |
| 无 frustum culling | `camera_contains_point` 有了，但渲染器还没用它剔除 | M3/M4 |

## 十、给后续阶段的提醒

1. **M3 的 2D 批渲染必须走 `renderer_push_item` 这条路**，
   不要绕过渲染队列直接调后端。批处理的价值就在于"排序后合并同管线的 draw"。
2. **`render_backend_t` 接口一旦定下，后续后端只做实现，不改接口。**
   如果实现 D3D11 时发现接口不够用，先想清楚"是不是 GL 实现绕过了抽象"，
   再考虑改接口。
3. **`GL_CHECK()` 只在 Debug 生效**，不要放进每帧的热路径循环里
   （`glGetError` 会强制刷新命令队列）。
4. **新加 GL 常量时，务必在开着调试回调的情况下跑一遍** ——
   手抄常量的错误只有它能抓出来。
5. **`RENDER_UNIFORM_BLOCK_GLSL` 改动时必须同步 `uniforms.h` 的 C 结构体**，
   两边的 `_Static_assert` 与测试会兜住，但改的人要知道它们是一对。
