## 一、验收结论

| 验收项 | 结果 |
|---|---|
| 多光源 + 阴影 | 5 盏灯（2 平行光 + 2 点光 + 1 聚光），2048² 阴影贴图 |
| 模型查看器 | `05_model`：左键环绕 / 右键平移 / 滚轮缩放，OBJ 与 .mesh 均可加载 |
| 渲染目标抽象 | `render_target_t`：颜色 + 深度附件、MSAA 解析、resize 重建 |
| sRGB 管线理顺 | 端到端读回像素断言通过（见第三节） |
| 视锥剔除可观测 | 剔除开 117 draw call / 关 133，差 16 次（8 个物体 × 阴影+主通道） |
| 上层不直接调 GL | 保持：示例与渲染核心里没有 `gl->` |
| 单元测试 | 289 用例 / 20658 断言全过；Debug + Release + `-Werror` + ASan/UBSan 四档零告警零报错 |
| 内存 | 退出零泄漏 |
| 帧时间 | 16.345 ms 平均 / 16.784 ms 最大（vsync 开，60 FPS） |

### 1.1 与计划的两处偏离（都是有意为之）

| 计划 | 实际 | 理由 |
|---|---|---|
| `skybox.h` 独立模块 | 程序化渐变天空做在 `renderer.c` 的 present 之后 | 天空盒只是"按视线方向算颜色"，没有资源、没有状态，独立成模块只会多一层传递。等 M6 需要 cubemap 时再拆 |
| `gltf_loader.h` | 改为自研二进制 `.mesh` + `tools/mesh_tool` | M4 提示词本身就允许"先只做 OBJ + 自研二进制格式"。GLTF 推到 M7 和资源管线一起做（异步加载、打包、世代句柄），那时候加载器才有正确的宿主 |

## 二、本阶段最大的一次坑：GL 枚举值写错 = 驱动踩栈

### 2.1 症状

`05_model` 一启动就段错误，日志停在

```
DEBUG TRACE: 开始 std140 校验 (builtin:present)
DEBUG TRACE: 查块 FrameUniforms
DEBUG TRACE: index=0
```

而且**不是 M4 才有的问题**：`02_render`、`04_breakout` 全部一起崩。
崩的位置在一行看起来完全无害的代码上：

```c
LOG_DEBUG("TRACE: gpu_size=%d expected=%llu", (int)gpu_size,
          (unsigned long long)blocks[i].expected);
```

### 2.2 定位过程（值得记下来，下次照抄）

1. **ASan 构建不崩，普通构建崩** —— 说明是内存问题，不是逻辑问题。
2. 加 `fprintf(stderr, ...)` 逐步二分（stderr 不缓冲，日志文件是缓冲的，
   所以"最后一行日志"骗人）。
3. 崩溃点后移到 `log_printf` 的**函数体之前**：`LP0` 探针根本没打印。
4. 在示例里挂 `AddVectoredExceptionHandler`，拿到硬数据：

   ```
   code=0xC0000005（读越界） fault=0x...7F5D5278 rsp=0x...7F5D51A0 image=0x7FF6AF3D0000
   ```

   `fault - rsp = 0x50_0000_00D8`，**三次运行偏移完全一致**。
   不是随机踩踏，是确定性的坏地址 —— 说明有个"值"被当成了索引。
5. `rip - image_base = 0xDF7D`，`llvm-objdump` 反汇编那几条指令：

   ```asm
   movq   0x88(%rsp), %rcx     ; 循环计数器 i
   leaq   0x90(%rsp), %rax     ; blocks 数组基址
   shlq   $0x4, %rcx           ; i * 16（元素大小）
   addq   %rcx, %rax
   movq   0x8(%rax), %rdx      ; <== 崩在这里：blocks[i].expected
   ```

   反推 `i = 0x500000004`。栈上的循环计数器被改写了。
6. 谁改的？把 `glGetActiveUniformBlockiv` 的目标从 `GLint gpu_size`
   换成一个带哨兵的 `GLint guard[10]`，结果：

   ```
   guard after = 1 2 4 5 6 7 8 9 10 11
   ```

    initialized 成 0x5A5A5A5A 的十个元素全被覆盖 —— 驱动按"数组"在写，
   而我们只给了一个 int 的空间。

### 2.3 根因

```c
#define GL_UNIFORM_BLOCK_DATA_SIZE 0x8A43   // 错
```

`0x8A43` 是 **`GL_UNIFORM_BLOCK_ACTIVE_UNIFORM_INDICES`**，
它的语义是"把这个 uniform 块里的 uniform 索引列表写进 params"——
于是驱动往我们给的 4 字节栈变量后面连续写了 N 个 int。
正确的值（`glcorearb.h`）是：

```
GL_UNIFORM_BLOCK_DATA_SIZE              0x8A40   单个 int：块占多少字节
GL_UNIFORM_BLOCK_NAME_LENGTH            0x8A41   单个 int：名字长度
GL_UNIFORM_BLOCK_ACTIVE_UNIFORMS        0x8A42   单个 int：块内 uniform 数
GL_UNIFORM_BLOCK_ACTIVE_UNIFORM_INDICES 0x8A43   整数**数组**，长度 = 上一条
```

四个常量只差末位，写错了 **GL 不会报错**（pname 是合法的），
只会按另一种语义使用你的指针。

### 2.4 这条坑的普适教训

- **"诊断代码"出的错，比它要诊断的错更难查** —— 因为它从来没被当成被测对象。
  一个只读查询写成了数组语义，就把栈踩了。
- 手抄 GL 枚举是高危动作。凡是新加枚举，**必须让驱动反过来证明自己**：
  查出来的值要和 CPU 侧已知量对上（`sizeof(frame_uniforms_t) == 1024`），
  对不上就说明读的东西不对，而不是"返回了个奇怪的数"就放过。
- `ASan 不崩 / 普通构建崩` 不是"ASan 误报"，而是栈布局变了把越界刚好藏住了。
  这时应该**加哨兵**而不是换构建档继续跑。

修好之后 std140 校验反过来成了一条有用的断言：所有着色器的
`FrameUniforms` GPU 侧 1024 = C 侧 1024，`ObjectUniforms` 176 = 176。
它同时也证明了光源数组在 std140 下的对齐没问题 —— 那是第五节要防的坑。

## 三、sRGB 管线：把 M2/M3 欠的账一次还掉

### 3.1 决策

| 环节 | 空间 | 说明 |
|---|---|---|
| 颜色贴图（albedo） | **sRGB 格式存储** | 采样时由 `sampler2D` 自动解码到线性 |
| 光照 / PBR 计算 | **线性** | 光照必须在物理正确的线性空间做 |
| 离屏场景目标 | **线性**（RGBA16F/RGBA8 线性格式） | 中间结果不能被编码两次 |
| 窗口帧缓冲 | **sRGB 编码** | present pass 输出时编码回 sRGB |
| 色调映射 | 线性空间、present 之前 | ACES，可选关闭 |

### 3.2 客观验证（不能靠眼睛）

sRGB 错的表现为"整体偏暗"，而所有东西一起偏是肉眼判不出来的。
所以 `05_model --srgb-check` 渲染已知灰度并**读回像素断言**：

```
线性值      场景目标   窗口(sRGB)   期望    结果
0.00000     0          0            0       通过
0.21586     55         128          128     通过
0.50000     127        187          188     通过
1.00000     255        255          255     通过
```

判据是独立的：`0.21586` 是 sRGB 128 反解出来的线性值，
`128` 是它再编码回去应有的字节。场景目标读到 55（= 0.21586×255）
证明它存的是线性值，窗口读到 128 证明编码只发生了一次。

（187 vs 期望 188 在容差内：线性 0.5 存进 8 位目标已经量化过一次。）

## 四、渲染目标与 MSAA

`render_target_t` 描述：颜色附件（格式/数组层/多重采样）+ 可选深度附件 + 名字。

- **MSAA 缓冲不能直接采样。** `samples > 1` 时额外建一个 resolve FBO，
  绑定切走之前 `glBlitFramebuffer` 把多重采样内容解析到单采样纹理，
  调用方采样的一直是那张单采样的。`needs_resolve` 标记防止重复解析。
- **resize 必须重建所有附件。** 只更新颜色不更新深度会让帧缓冲"不完整"，
  而 GL 对不完整帧缓冲的态度是**静默丢弃所有绘制** ——
  症状是"窗口一缩放画面全黑"，日志里干干净净。
- **深度约定全阶段一致。** M0 定死深度 [0,1]（`glClipControl`），
  阴影通道的离屏目标同样遵守；漏掉的表现是"主视图正常但阴影全错"。
- 本阶段用了两个目标：`shadow_map` 2048² 深度专用、`scene` 1280×720 samples=4。

## 五、多光源：一次 draw，不是每盏灯一次

- 所有灯进 `FrameUniforms` 的 uniform **数组**，一次 draw 画完整个场景。
- CPU 侧结构体与 GLSL 块的一致性由第二节的校验保证。
- std140 下数组元素按 16 字节对齐 —— 如果 C 侧结构体大小不是 16 的倍数，
  整个数组会错位，典型症状是"第一盏灯正常，后面的灯参数全乱"。
  `light_to_gpu` 与 `_Static_assert` 一起把这条钉住。
- `shadow_caster` 记录哪盏灯投影（集合里最多一个），
  其余灯只贡献光照不进阴影通道。

## 六、阴影贴图：参数与理由

| 参数 | 取值 | 为什么 |
|---|---|---|
| 分辨率 | 2048² | 单级联下 2048 在演示场景里边缘已经看不出阶梯；再高一档显存和带宽翻倍收益却很小 |
| 级联 | **不做**（单级） | CSM 的复杂度（级联选择、接缝、闪烁）远超本阶段收益。等出现"远处阴影糊成一片"再做 |
| 视锥 | `shadow_map_fit_directional` 紧凑贴合场景 | 平行光阴影贴图覆盖范围越大分辨率越低。用**包围球**而不是 AABB 来定尺寸：球对光源方向不敏感，AABB 会让阴影边缘随光源旋转而抖动 |
| 偏移 | `constant=2.5, slope=1.8, normal=0.035` | 三个都要：`polygonOffset` 治痤疮（表面条纹），normal offset 治自阴影痤疮，值太大就变彼得潘（阴影和物体脱开）。偏移参数变化后**需要重建管线才生效**，日志里已注明这一点 |
| 只画投影者 | 阴影通道只画不透明投影物体 | 阴影通道耗时通常等于甚至超过主通道 |

## 七、视锥剔除

- `frustum_t` 六个平面，从 view-projection 提取（列主序 + 右手系 + 深度 [0,1] 三者叠加）。
- 测试**不靠手算点**，靠独立判据交叉验证：用裁剪空间不等式
  （`-w<=x<=w`、`0<=z<=w`，且 `w>0`）作为"定义"，和实现的每个方向对比，
  包含斜置相机的情况。手算的点只覆盖几个方向，恰恰容易漏掉提取错误。
- AABB 剔除是**保守**的（宁多画不漏画），测试专门验了"AABB 判定比点判定更宽松"这一条。
- 退化矩阵（全零）下**永不剔除** —— 出错时宁可多画，也不要画面凭空少一半。
- 可观测性：主循环每帧上报被剔除物体数；`--no-cull` 或按 `6` 切换，
  直接对比 draw call 数（117 / 133）。

## 八、`.mesh`：自研二进制网格格式

### 8.1 分工

| | `.obj` | `.mesh` |
|---|---|---|
| 角色 | 源格式，人可读可写 | 运行格式，机器专用 |
| 加载 | 词法解析 + 面角重建 | 一次 memcpy + 头部校验 |
| 谁产出 | 美术导出 | `tools/mesh_tool` 离线转换 |

转换是离线的，代价只在导入时付一次；运行时每次启动、每次热重载都少付一遍解析。

**小模型上看不出差距**（立方体 0.836 ms vs 0.880 ms，两端都是读盘+解析，
读盘占主导）。解析成本随顶点数线性增长，收益要到几万顶点才明显 ——
`mesh_tool` 的输出里直接把这句话写出来了，免得有人拿一个立方体的数字下结论。

### 8.2 格式要点

- 头部固定 64 字节，**逐字段小端读写**，不做结构体整体拷贝：
  不依赖主机字节序、不依赖编译器的填充规则、不违反严格别名。
- 段顺序：头部 → 顶点表 → 索引表 → 名字。
- `vertex_stride` 显式写进头部并在加载时比对（32 = `sizeof(mesh_vertex_t)`）：
  顶点布局变了就是格式变了，硬读会得到错位的法线，症状是"模型歪了"。
- `reserved` 16 字节：写入恒 0，读取**不校验** ——
  校验它等于把"将来当 flags 用"的路堵死，而版本不兼容该由 `version` 负责。
- 索引越界在交给 GPU 之前必查。驱动越界读不会报错，只会随机花屏或丢上下文。
- 数量 × 元素大小的溢出要在**分配之前**拦住，否则就是
  "读一个坏文件 → 申请天文数字内存 → 失败 → 解引用 NULL"。
- 测试里对字节布局的判据是头文件那张偏移表，**不是 `mesh_file_build` 自己** ——
  往返一致只证明编解码自洽，一个把字段顺序写反的实现同样能自洽地往返。

### 8.3 一处实现自查

`mf_elem_bytes` 最初"返回 0 表示溢出"，于是 `index_count == 0`
（非索引图元，合法）被当成错误全拒了。改成显式 `bool` + 出参。
**"用特殊返回值编码失败"在 0 是合法值的场合一定会踩。**

## 九、ASan 顺带抓出的两处 M3 既有越界

都不是 M4 的代码，但既然 ASan 抓到了就一并记下（它们一直在那里）：

1. `tests/test_atlas.c` 的 `atlas_regions_do_not_overlap`：
   缓冲区按 `32*32*4` 开，循环里却请求到 `40×40` 的区域，
   图集按 `w*h*4` 拷 → 越界读 6400−4096 字节。
2. 同文件 `atlas_write_region_copies_pixels`：
   `source` 是 `4*4*4`，却调用 `write_region(..., 16, 16)`。
   引擎按 `width` 做行 stride 读源，于是读到源末尾之后 64 字节。
   该用例的本意是"源比区域大时目标不能溢出"，那源就该真按 16×16 开。

**两处都是测试自己撒谎，不是引擎的错** —— 引擎无从知道缓冲区实际多大。
但这正说明"Release 全绿 + 无泄漏"不等于内存安全，ASan 那一档不能省。
