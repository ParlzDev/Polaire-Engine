## 二、本阶段最大的一次坑：一个少写的 `+1`，症状是"程序卡死"

### 2.1 症状

06_scene 的 `--bench 200` 慢到没跑完，交互模式却完全正常。分段计时之后：

```
  [A] 纯 ecs_world_update       638.563 ms/帧     ← 200 个实体
  [B] 第 0 次：重建 19043.917 ms | 世界矩阵 0.112 ms | 系统 0.023 ms
      | 节点 200 深度 3452816846                  ← 深度是个三十亿的数
```

`ecs_rebuild_hierarchy` 一次调用 19 秒。世界矩阵和系统都是零点零几毫秒，
说明不是数学慢，也不是查询慢。

### 2.2 定位过程

1. 先把 `ecs_world_update` 拆成三段分别计时（重建 / 世界矩阵 / 系统本体）。
   **"world_update 很慢"这一条数字没有下一步信息**，拆开才有。
2. 每个数字都跟着打印 `ecs_hierarchy_depth_max_seen`，于是看到 3452816846。
3. 重排的第二趟是 `for (d = 0; d <= max_depth; ++d)`。`max_depth` 由数据决定 ——
   三十亿层循环，就这么来的 19 秒。
4. `max_depth` 来自 `depth_cache[handle_index(e)]`。这个缓存每帧先整体重置为
   `ECS_DEPTH_UNKNOWN`，所以"没算过"的格子才会去算链长。
   问题在**重置的界限**：`for (i = 0; i < pool_capacity(); ++i)`。
5. 而 `pool_alloc` 发出去的最大 index 正好等于 `pool_capacity()`
   （0 号槽保留，`capacity = slot_count + 1`，`pool_capacity()` 又减回 1）。
   于是**最后一个实体的那一格从来没被初始化过**，读出来是堆上的残留字节。
6. 复现条件苛刻得很：必须"实体数正好等于容量"，也就是把池子填满。
   交互模式 13 个实体、单元测试容量 64 用不满 —— 所以它只在 bench 出现。

### 2.3 根因与修法

```c
// 以前：三处各算各的，全都少一项
const u32 index_space = pool_capacity(&world->entities);
// 现在：一个地方算，三处都过它
static inline u32 ecs_handle_index_space(const ecs_world_t *world)
{
    return pool_capacity(&world->entities) + 1u;
}
```

同一个式子还漏在 `row_of`（u32 数组）与 `presence`（位图）上 —— 那两处是**越界写**，
比读更糟。收成一个 inline 函数之后，`ecs_storage_t` 里存的 `index_space` 与
释放时用的式子天然一致（以前分配按 index_space、释放按 capacity，
是同一类的两本账）。

### 2.4 两件值得记住的事

- **ASan 抓不到它。** 那格越界读落在分配器向上取整出来的可访问区里，红区还没到。
  最后能靠的是**兜底计数**：给重排加一条"深度超过 `hierarchy_depth_max` 就当根节点
  并计数"，测试断言 `hierarchy_rejected_cycles == 0`。把 `+1` 去掉，这条测试就红。
  换句话说：一个断言若能被兜底掩盖，就必须另外留一条"兜底不该被触发"的断言。
- **一个坏数据不该有能力把一帧变成十分钟。** 越界是根因，但"循环上界由数据说了算"
  是第二道失守。两处都补了。

### 2.5 修完之后的数字

## 三、第二处越界：dense id 销毁后不回收（比第二节更难发现）

`record->dense_id = world->next_dense_id++;` —— 只涨不降。它的语义是
"这个世界**总共创建过**多少实体"，而 `dense_to_entity` 只有 `entity_capacity` 项。

后果链：编辑器里删一个建一个 → 水位线顶到容量 → 新实体的 dense 越界 →
`ecs_rebuild_dense_index` 按 `dense < capacity` 守卫把它跳过 →
**它不出现在 `ecs_collect_entities` 里，也就永远不会被存盘**，且一路不报错。

修法是一个空闲号栈：销毁时归还、创建时先取，两边都是 O(1) 且不需要遍历。
另外 `ecs_world_clear` 把水位线归零时必须**同时清空栈**，否则同一个 dense 会发两次
（重复 dense 的存档会让两个实体的组件互相覆盖，所以读侧也加了"同一个 dense 出现两次
就整份拒绝"的校验）。

这条也配了会真红的测试：把复用关掉，第二次批量创建直接失败、collect 只到一半。

顺带发现并补掉：`ecs_world_create` 里"命令队列初始化失败"那条错误路径把前面
拿到的四块内存全丢下了（分配失败的清理以前只写了一半）。

## 四、序列化：一套字段遍历，四处必须说话

（决策 D3 的落地，`src/scene/scene_io.c`）

1. **绝不整块 memcpy。** 把结构体原样写进文件，等于把编译器的填充规则写进格式：
   换编译器、加字段、调成员顺序，存档就**静默错位**，症状是"读出一堆乱值且不报错"。
   按字段表逐字段读写，padding 一字节不落地。
   于是 `vec3_t` 内存 16 字节（含 pad）、文件里 12 字节 —— 这两个数必须分开算，
   写成一个就是"组件声明长度比实际写出的多 4，从第一个含 vec3 的组件起全体错位"。
2. **长度可以纯从表算出来**，所以每个组件都带精确的负载长度。
   这条能力换来的是"不认识的类型整块跳过、后面的实体照常读"，
   而不是"一个坏组件毁掉整个场景"。
3. **实体拆成索引段 + 数据段。** dense id 重映射要一遍线性完成：
   索引段先把所有实体建出来并填好映射表，数据段再翻译父子与组件内的实体引用。
   否则得给字节流加 seek —— 多一个 API、多一处能写错的地方，省下的只是每实体 12 字节。
4. **资源引用落名字，实体引用落 dense id。** 句柄和下标都是"这一次运行"的产物；
   落索引的话，在资源列表中间插一行就让后面全体错位，**而且读得出来**
   （只是"这个模型穿了那个模型的皮"）。
5. **写出侧也报 `dangling_refs`。** 组件里存着越界的资源下标，在存盘那一刻就已经是 bug；
   等到读盘才报，文件里只剩一个空名字，连"这里曾经有过一个坏引用"都没留下 ——
   那是把案发现场擦掉再报警。

还有一条实现自查：长度自检。存档总长由"先量一遍"算出，写完比对
`bio_writer_used() == total`。它在本阶段抓到了三个不一致（vec3 尺寸、资源段的
假计数前缀、实体数据段照抄了索引段的 12 字节）。只在函数末尾比总长的话，
能得到的只是"差了几个字节"，差在谁身上没人知道 —— 所以每条记录都就地核对
"字段表算出的长度 == 真写出去的字节数"并点名是哪张表。

## 五、预制体：一段带根的存档字节

`prefab_t` 持有的就是 `scene_write_prefab` 产出的字节副本，实例化走的是读档入口。
没有第二套格式，也没有第二套校验。

- 校验只留一处。"加载时没报错、实例化时才报错"是最难说的状态；
  而预制体唯一被消费的一刻就是实例化，那时本来就必须完整读一遍。
- 与整场景存档的三点差别：**只写子树**（dense 在子树内从 0 重编号，
  引用子树外的实体一律变 NONE —— 预制体不许偷偷依赖外面的东西）；
  **只写被引用到的资源**（连带材质→图集那层依赖）；环境块写默认值且读侧不应用。
- "只带被引用的资源"不是优化而是必需：不这么做的话，实例化一个炮塔会把源场景
  整张资源表灌进目标场景，而资源表上限是 128，第三次实例化就失败，
  日志看着像"表满了"。
- 实例化不回滚半途失败的东西：回滚要把那批实体按 dense 找回去、还要处理它们
  已经挂好的父子关系，那套代码出错的概率比它留下的问题更大。所以根实体照样交回，
  返回值说失败，要不要销毁由调用方决定。

实测：一个 3 实体的柱子预制体，100 次实例化 17.4 ms（0.174 ms/次），
资源表按名字去重所以始终只有 1 个网格 1 个材质。

## 六、格式的一条性质：加载会压实 dense

"存 → 读 → 再存**逐字节相同**"这句验收判据要说准确：

实体销毁后 id 不回收，所以编辑器里存出的第一份存档 dense 列是带洞的
（0,1,2,4,6）。读进一个新场景时实体是按文件顺序创建的，于是再存出来是
0,1,2,3,4 —— 这两次**内容相同但字节不同**。从第二次起进入规范形，
往后怎么往返都逐字节一致。

所以判据是"任意场景读一遍之后，往返逐字节一致"。`scene_io/dense_holes_canonicalize`
这条测试同时钉住两件事：压实前后内容对得上（名字与它的相机参数必须还挂在
同一个实体上），以及规范形之后逐字节相同。

## 七、ECS → 渲染的桥接层（`src/scene/ecs_submit.c`）

这是 M5 里唯一同时看得见 `ecs/` 与 `render/` 的位置，依赖方向单向：
`scene -> ecs + render`，谁都不反过来依赖谁。

1. 提交走渲染队列而不是直接画：批渲染要"同纹理同管线连续"，而 ECS 的迭代顺序
   是内存顺序。所以 3D 走 `renderer_push_mesh`（内部排序），2D 走 sprite_batch。
2. **投射阴影的那盏灯必须排在 0 号位**（M4 的 shader 判的是 `i == 0`），
   所以桥接层收完光源后会把阴影投射者换到前面。这条约束写在代码里，
   因为它是"shader 与 C 结构体的约定"，只在一侧说明等于没说明。
3. 精灵只在 layer 变化时 flush，**不逐精灵改 depth**：后者会把 M3 辛苦做的合批打回原形。
4. 相机朝向从世界矩阵的 3x3 取（先去掉缩放）。这条是本阶段补的：
   以前桥接层固定给单位四元数，于是"相机挂在会转的父节点下面"根本不生效 ——
   而轨道相机恰恰就应该是"某个会转的节点的子节点"，不需要一行特例代码。
5. 06_scene 把 `scene_submit_frame` 放在系统外面而不是 RENDER_SUBMIT 阶段：
   `renderer_begin_frame` 要一个相机，而相机得从**本帧已算完的**世界矩阵里取。
   做成系统就得先 begin_frame 再 update，那台相机只能是上一帧的。

## 八、"名字已登记、句柄待绑定"是一个中间态，不是将就

`scene_add_mesh_pending` / `scene_add_atlas_pending` + `scene_pending_resource_count`。

存档里"程序化资源"没有文件路径，引擎无从创建 GPU 对象，但**必须**先把表槽位建出来
（组件存的是下标）。以前这里调的是 `*_handle(..., INVALID)`，而连着渲染器的场景
会拒绝无效句柄 —— 等于"存档里有一个程序化网格"就"在有 GPU 的场景里读不出来"。

三层结构因此需要一个明确的第三层入口：
**存档 → 名字（人可读、跨运行不变）／运行期 → 表下标（一次加载内不变）／
GPU → 句柄（随时可换）**。热重载（M7）要做的正是换第三层而前两层不动。

06_scene 加载完打印 `未就位 2 个 → 绑定后 0 个`。"场景读成功了但画面是空的"
这种现场，有这一个数就能一句话分开。

## 十一、JSON 形式：做成了"转码"，而不是第二套序列化器

计划的验收原文是"二进制与 JSON 两条路往返一致"、"两者可互相转换"。
最直觉的实现是往 scene 上再挂一套遍历（写 JSON、读 JSON）。**没这么做**，
理由是那会让下面这些问题各自有两份答案：

- 哪些实体进存档（整个世界，还是 root 的子树）；
- 按什么顺序（顺序不定，"逐字节比对"这条判据就直接失效）；
- 引用子树外的实体怎么算、dense id 从哪重新编号；
- 预制体带哪几条资源（漏了过滤就是第三次实例化把资源表撑爆 —— 第二节那个坑的近亲）。

两份答案会一致到有人改了其中一边为止。所以 `src/scene/scene_json.c` 只做一件事：
**存档字节 ↔ JSON 文本**。导出走 `scene_io_write_archive()` 出二进制再展开成文本，
导入把文本编回二进制再交给 `scene_io_read_archive()`。
于是策略全工程只有一份，校验也只有一个守门人。

转码之所以可能，是因为二进制格式自己就是自描述的：资源引用落**名字**、
实体引用落 **dense id**、每条记录的长度可纯从字段表算出 ——
两个方向都不需要"句柄→索引→名字"这种必须问活的 renderer 的翻译。

### 11.1 类型表必须同源，否则字节永远对不上

第一版的 JSON 导入按"文档里名字首次出现的顺序"给自己编类型表。
读进来场景完全正确，但"二进制 → JSON → 二进制"的字节**不等**：
类型表那一段顺序不同，每条记录里的类型下标也跟着全体错位。

改成两边都用 `scene_serializable_types(world)`（同一个函数、同一个顺序）。
这个坑值得记的是一般形式：**跨实现的相等性判据，会把"实现细节里的自由顺序"变成格式的一部分。**
只要两处各自决定一次顺序，判据就不再是"数据相同"而是"两份决定碰巧相同"。

### 11.2 两类失败必须分开处理

| 类别 | 例子 | 处置 | 为什么 |
| --- | --- | --- | --- |
| 文档写坏了 | 向量少一个分量、顶层键拼错、一个实体里两条同类型组件、名字超容量 | **整份拒绝**并点名 | 和 `json.c` 同一条规矩："能读出一半"会让人以为文件没坏 |
| 版本漂移 | 类型名本构建不认识、字段名不在该类型的表里 | 跳过该类型并**按类型计数** | 二进制那边就是整块跳过，两种编码必须给同一个答案 |

一处**有意**的不对称：二进制遇到 schema 哈希不符会拒绝整个类型，即使缺的字段本可以用默认值补；
JSON 允许只写关心的那几个字段。因为二进制是引擎写给引擎的，而 JSON 是写给人的 ——
"我只改曝光，别的保持原样"必须是合法诉求。默认值取自**默认记录**
（组件 `construct`、环境 `scene_env_default()`、材质 `material_default()`），
所以"JSON 里没写的字段"和"代码里新加的组件"永远是同一个值。

省略字段这条规则差点写错：`u32` 一开始和 dense id 共用了取值函数，
于是"没写 layer"变成 `layer = 4294967295`，症状是"物体读进来了却怎么都不显示"且不报错。
`tests/test_scene_io.c: json_omitted_u32_keeps_default` 钉住它，
而环境块那几条断言拿"默认值非零"的字段（`msaa_samples=4`、`tonemap_mode=1`）当探针 ——
用 0 当默认值的字段做不了这个探针，因为它和"错的 0"看起来一样。

### 11.3 一条二进制没有、必须显式选的差别：浮点文本

二进制走小端 f32 位模式（无损）。JSON 用 `json.c` 的最短可往返十进制
（从 1 位有效数字往上试，第一个能读回同一个位的就输出）。
固定 `%.9g` 同样无损，但会把 `0.1f` 写成 `0.100000001` —— 场景文件是给人手改的。
另外 JSON 没有 NaN / Infinity 的字面量，所以**含非有限浮点的场景存不成 JSON**
（`json_write_f32` 拒绝，`json_rejects_non_finite` 钉住"二进制能存、JSON 明确报错"这条差别）。

为了让人手改的文件真的能改，`json.c` 补了 `json_begin_array_inline()`：
向量写成 `"position": [0, -0.3, 0]` 而不是四行。同一份演示场景从 13887 字节降到 11607 字节，
而"逐字节相同"的判据不受影响（排版是确定的）。

### 11.4 判据分三层，缺一不可

1. **纯转码无损**：二进制 → JSON → 二进制逐字节相同（不经过场景，所以 dense 压实之类的
   正常规范化掩盖不了真正的丢内容）；反方向 JSON → 二进制 → JSON 文本相同。
2. **跨编码等价**：场景 A 的二进制 与 (A→JSON→场景 B) 的二进制逐字节相同。
3. **文本自稳定**：JSON → 场景 → JSON 文本相同，三轮不漂（每存一次盘场景变一点的 bug 就在这儿现形）。

再加两条工程性的：读档的临时内存（DOM + 中间二进制 + 三张表）用完必须整体 rewind，
`json_text_is_stable` 里按"scratch 用量回到读档前"断言 —— 这类泄漏前 99 次都不会失败；
以及 `scene_load_auto()` **先看内容再看后缀**（魔数四个字节），因为手改文件名是常态，
而后缀猜错的报错（"第 1 字节语法错误"）指向完全错误的方向。

## 十二、让世界矩阵的求值挂在**阶段**上，而不是挂在"有没有系统注册在那"

### 12.1 症状：计数器在涨，屏幕上不动

`--check-pixel` 里那条"动根节点，叶子必须跟着动"的验证第一次跑就红了：

```
父子链验证未通过：根节点世界位置变了 +0.0000/+0.0000/+0.0000，
同一次更新里叶子变 +0.0000/+0.0000/+0.0000，再更新一次叶子变 +0.0000/+0.0000/+0.0000
```

**连根自己的世界矩阵都没动。** Spin 系统在跑（`systems_run`、Spin 计数都在涨），
本地变换也确实被改了 —— 只是世界矩阵这一层根本没人重算。

### 12.2 根因

`ecs_world_update` 老实现的形状是"遍历系统数组，遇到第一个 TRANSFORM 阶段的系统时
顺手调一次 `ecs_update_world_transforms()`"。于是：

- 没有任何系统注册在 TRANSFORM 阶段的世界里，世界矩阵**永不重算**；
- 而 06_scene 正是这种情况（提交在 `ecs_world_update` 之外，示例只在 LOGIC 注册了 Spin）；
- 结尾那条兜底 `if (hierarchy_dirty && system_count > 0)` 也被 `system_count > 0` 挡住。

症状不是崩溃、不是报错，而是"数据对了，画面不动"。
D4 把"求值顺序"当成一等设计问题（慢一帧就是抖动），但顺序对了也没用 ——
如果那一阶段的**触发**依赖某个可选的系统注册。

### 12.3 修法与教训

改成按**阶段**走：`for stage in 0..COUNT` → 边界 flush 延迟命令 →
`stage == TRANSFORM` 时求值世界矩阵 → 跑该阶段的系统。系统数组本来就按
`(stage, priority, name)` 全序排好，所以内层是一次线性推进，代价为零。

教训有两条，都值得记下来：

1. **阶段调度的语义属于阶段，不属于该阶段里的系统。** "这一帧要在 RELATION 之后、
   RENDER_SUBMIT 之前算一次世界矩阵"是引擎的固定契约；把它实现成某个系统的副作用，
   就等于把契约交给"记得注册"的人。
2. **测内部函数不等于测入口。** 原有的层级单测全部直接调 `ecs_update_world_transforms()`，
   所以全绿 —— 它们测的是求值数学（那部分确实没错），
   而缺陷在"谁在什么时候调用它"。补的回归测试
   `ecs/world_transform_updates_via_world_update` 刻意**一个系统都不注册**、
   只走 `ecs_world_update()`，把入口那条路径钉住；去掉 12.3 的修法它会变红。

### 12.4 修好之后 ECS 那一档变慢了，而且必须变慢

| | 修前 | 修后 |
| --- | --- | --- |
| `[A] 纯 ecs_world_update` @1k | 0.027 ms/帧 | 0.054 ms/帧 |
| @10k | 0.472 ms/帧 | 0.622 ms/帧 |
| @100k | 7.488 ms/帧 | 6.350 ms/帧（@100k 是另一档，见第十三节表） |

1k / 10k 那两行**接近翻倍**，因为以前那段时间里世界矩阵根本没重算 ——
省下来的正是本该做而没做的工作。100k 反而变快是同一条判据在不同规模上的噪声
（那一档的世界矩阵本来就是主要成本，改动带来的差别淹没在测量抖动里）。

这条要记的不是数字，是**"优化让某个数变小"这句话在数字没有语义时不成立**：
如果只盯着"帧时间从 0.027 涨到 0.054"，正确的修复看起来像一次回归。
所以每个性能数字都必须写清楚它测的是哪一段工作，
而这一段工作的**定义**变了，旧数字就同时作废 —— 本节把旧数字留在原地并标出这一点，
而不是悄悄改掉它们。

## 十三、"看得见"的三条验证：像素、父子链、整帧墙钟

M5 的判据里有三条是"看得出"的：2D/3D 同帧共存、动父节点子节点跟着动、1000 实体 60 FPS。
三条都做成了**程序自己判、退出码说话**（CI 可跑），不靠人盯屏幕：

| 验证 | 做法 | 实测（Release / RTX 5060，跑两遍取第二遍） |
| --- | --- | --- |
| 父子链 ≥3 层 | 4 层链 `lamp_rig → arm → head → light`；dt=0 跑两帧，只动根，比对叶子的世界位移 | 动根 +3/-1.5/+2.25 → 叶子变化误差 **0.0** |
| 2D/3D 同帧共存 | 读回中间横带（1280×360），做两次扰动：摘掉精灵、挪走方块 | 精灵 **13344** 像素、方块 **59963** 像素、**重叠 0** |
| 动画真的上屏 | 连跑两帧真实增量（dt=1/60），画面必须变 | **2813** 像素变化（第十二节修之前这里是 0） |
| 整帧含 present | bench 加 `[D]` 相位：world_update + begin + submit + **end_frame（交换缓冲）**，墙钟计时，**并且按比例带上精灵**（1/10） | 1k 方块+100 精灵 **1.56 ms = 641 FPS** ✅；10k+1000 精灵 **8.51 ms = 118 FPS**（最差一帧 19.3 ms）；100k+1 万精灵 66.4 ms = 15 FPS（无门槛，只作基线） |

`[D]` 里那句"1 万静态方块 + 1000 动图精灵仍 60 FPS"是 M3/M4 挂到这里的判据
（M3 原文只要求 CPU 侧 < 16 ms，含渲染的那一半被写明"到 M4 末正式验证"，
而 M4 的示例里根本没有精灵）。现在它落在 06_scene 的 bench 上，
比例固定为实体的 1/10，所以三档规模都自动满足"混排"这一条。

三点要说清的：

- `[C]`（begin_frame + submit，不含 end_frame）是**CPU 侧录制命令**的成本，
  拿它当帧率就是把纯 CPU 数字当端到端数字用。`[D]` 才是"能不能真把画面送出去"。
- **墙钟含 present 的数不能只报一个标量。** 同一份二进制、同一串参数，
  实测过 1.56 ms 与 10.39 ms（1k 档）—— 差别来自驱动什么时候节流、别的进程有没有在用 GPU。
  所以 `[D]` 打印平均/最快/最差三个数，文档里的数字附复现命令与"跑两遍取第二遍"的条件。
  只印一个平均数，就是在教下一个人抄一个无法复现的标量。
- 100k 档的瓶颈是 GPU：`[A]` 6.35 ms + `[C]` 若干，而整帧 66 ms。阴影 pass 要把全部
  投射体再画一遍。这组数字是 M8（性能）的基线，不是 M5 的欠账。

"互不干扰"这条判据值得单独说一句：它不是靠"两边都画了"推出的，
而是靠**两次扰动的差异区不重叠**（重叠 0 像素）测出来的 ——
2D 盖住的地方挪 3D 也看不出来，所以重叠为 0 才说明两边各自独立地到达了屏幕。

## 十四、留给后面阶段的账

- **M6**：2D 精灵在 3D 相机下的屏幕映射规则。现在它以**世界单位**贴在场景里
  （`--check-pixel` 能读回它），但"HUD 那种屏幕像素坐标"仍未定义 —— 那是 M6 的核心内容。
- **M7**：资源热重载（按名字重新绑定句柄这条通道已经打通）、GLTF。
- **M11**：存档版本迁移（现在是"哈希不符就拒绝"）；
  材质记录里 8 个槽位名 = 512 字节的定长浪费，等有实测数据再换变长；
  编辑器属性面板（字段表已经够用，JSON 那一层的字段名也就是面板的标签）。
- **测试**：序列化还没有 10k 实体级的压力测试（往返正确性目前是逻辑级覆盖，
  不是规模级）；`scene_submit_*` 没有独立单测，只有 06_scene 在用 ——
  本阶段那个 96 字节查询泄漏就是它暴露的（示例里的 `spin_query` 忘了销毁）。
- **ECS**：`hierarchy_depth_max` 默认 32 是个约定而不是证明；
  dense id 现在会复用，所以"跨帧长期持有 dense id"这件事开始有语义风险，
  `ECS_FIELD_DENSE_ID` 的使用要等到 M11 的属性面板真需要它时再定规矩。

## 十五、决策 D1–D6 的落点，以及计划里那 12 条"预判坑"的逐条对账

计划的完成定义要求"记录定稿结论，包括 D1–D6 最终选了哪个、为什么"，
而"我预判的坑（请逐条确认或纠正）"要求**逐条**回答。前十一节是按踩坑顺序写的，
读起来找不到这两个清单，所以在这里补一张对照表 —— 内容不新，索引是新的。

### 15.1 D1–D6

| 决策 | 最终选择 | 记在哪 |
| --- | --- | --- |
| D1 组件存储 | per-type 稠密 SoA + 存在性位图；驱动池取最小基数 | 第一节表格 + 第四节（遍历与位图） |
| D2 组件注册与容量 | 注册时给容量上限（`pool` 不扩容），分配失败计数进世界统计，**不自动扩容** | 第三节的"容量是量出来的"；`ecs_world_stats_t.component_add_failures` |
| D3 字段描述表 | 表驱动序列化 + `offsetof` 断言 + schema 哈希；**没有做通用反射** | 第四节；JSON 那层见第十一节 |
| D4 世界变换 | 拍平拓扑序、无递归、脏标记延后重建 | 第二、三节（两个真实 bug 都在这条链上），第十二节补了"求值挂在阶段上" |
| D5 系统调度 | 固定 7 阶段 + `(stage, priority, name)` 全序 + 延迟结构变更 | 第十二节（这一条被修过一次） |
| D6 句柄与实体 id | `entity_t = handle_t`（24+8）+ **FIFO 轮转**放大代际回绕周期 + 序列化落 dense id | 第一、三节 |

**D3 的两处偏离要写清**：计划里的 `ecs_field_kind_t` 草案还列了
`ECS_FIELD_ENUM` 与 `ECS_FIELD_STRUCT`（以及 `struct_type` 字段），实际实现**没有这两类**。
理由：枚举用 `U32` 落盘完全够（存档里 `layer`/`projection` 就是 u32），
而"内嵌已注册的小结构"会把字段表变成递归结构 ——
那时"长度可纯从表算出"这条性质需要一套遍历规则来支撑，
而 transform 的三个成员拆成三个字段就够了。
计划里 D2 的 `component_desc_t` 也没有 `capacity` 之外的一致性要求，
实际的 `ecs_component_desc_t` 多了 `skip_serialize`（派生数据不能进存档，见第十二节）——
这条是计划没预料到但必须有的。

### 15.2 十二条预判坑

| # | 预判 | 结果 |
| --- | --- | --- |
| 1 | 迭代时改结构 | **成立**。命令队列 + 阶段边界 flush；`ecs_world_update` 开头检查"还有活跃迭代器"就报错并复位（不然会每帧卡在同一条错误上） |
| 2 | 组件里放裸指针 | **规则成立、文字没落文**（本次补上）。字段种类里**根本没有指针 kind**，所以"存了再读出来是野指针"这条路在格式层就不存在；prefab 复制的是字节，也不会有野指针 |
| 3 | 字段表与结构体漂移 | **成立**，且比预想的更凶：每个内置组件都有 `_Static_assert` 钉 offset，注册时算 schema 哈希，存档头比对不符就拒 |
| 4 | per-type pool 容量猜错 | **成立**。`component_add_failures` + 峰值统计进了世界统计，实测把容量从"拍脑袋"改成"量出来的"；同名组件抢注会被拒（只发一个 id） |
| 5 | 父子环 | **成立**。`ecs_set_parent` 上溯检测 + 深度上限；额外踩到一条计划没列的：垃圾深度值能把"按层重排"的循环拉长到几十亿次（第二节） |
| 6 | 世界变换别用递归 | **成立**，D4 因此选拍平拓扑序 |
| 7 | 合批与 ECS 迭代顺序冲突 | **成立**。提交一律进 `render_queue`/`sprite_batch` 排序，桥接层不直接 draw（第七节） |
| 8 | 2D 与 3D 的 transform 语义不同 | **成立但没解决**——正确处置是**共用一份 Transform**（没做成两套），而"2D 的像素映射、z 当层内排序键"这套规则归 M6。第十三节的精灵现在用世界单位，就是这个未决问题的现状 |
| 9 | 驱动池选错会退化成 O(全部实体) | **成立**。构造时按最小基数挑，且 `ecs_query_driver_name()` 把选了谁暴露出来（不打印选择的话，退化只能靠帧时间反推） |
| 10 | "能读回来"不等于"读对了" | **成立且是本项目最划算的一条判据**。三方对比（原→存 A→读→存 B，A==B）逐字节；JSON 那层再加三层（第十一节 11.4） |
| 11 | float 进存档的精度争议 | **成立**。二进制落位模式；JSON 用最短可往返十进制（比计划建议的固定 `%.9g` 更可读，同样逐位可逆，见 11.3） |
| 12 | JSON 解析器的边界 | **成立**。`test_json.c` 备了负面用例：截断、超深嵌套、非法转义、重复 key、越界数字、尾部垃圾、非有限值 |

一句话总结这 12 条：**11 条命中，1 条（#8）以"推迟到 M6"收口**。
而真正计划外的收获是另外两个 —— 第二节的少写 `+1`（卡死）与第十二节的
"求值挂在系统上"（画面冻结）：两个都不是崩溃、不报错，
都靠**数字与像素**才看得见。所以 M5 之后"验收"这件事的形状变了：
不再问"跑起来对不对"，而是问"哪一段数字会替你说谎"。
