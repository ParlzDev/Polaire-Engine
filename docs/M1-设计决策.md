# M1 设计决策记录

> 记录 M1 阶段所有"为什么这么做"以及踩过的坑。
> 改 M1 的代码前先读这里；改动后如果推翻了某条决策，请把这一条也一起改掉。

---

## 一、分层与构建

### 1.1 core 层需要平台能力时，用"端口"而不是反向依赖

M1 有两个地方 core 层需要平台能力：

| 需求 | 端口声明位置 | 实现位置 |
|---|---|---|
| 控制台 ANSI 支持 | `include/engine/core/console.h` | `src/platform/win32/win32_console.c` |
| 互斥量 | `include/engine/core/thread.h` | `src/platform/win32/win32_thread.c` |

做法是**接口声明在 core、实现在平台层**。这样 core 不构成对 platform 的依赖
（core 永远不 include `engine/platform/*`），依赖方向保持单向。

如果反过来让 core 去 include 平台头文件，分层就名存实亡了 —— 而"平台层"的价值
恰恰在于"换平台只改 src/platform 下的文件"。

### 1.2 为什么互斥量用定长字节缓冲而不是不透明指针

日志模块需要把互斥量作为**结构体成员内嵌**，而不是再分配一次。
内嵌要求编译期知道大小，所以：

```c
typedef struct platform_mutex_t {
    _Alignas(16) u8 storage[64];
} platform_mutex_t;
```

`win32_thread.c` 里有 `_Static_assert(sizeof(CRITICAL_SECTION) <= 64)` ——
放不下会直接编译失败，而不是运行期把栈写坏。

### 1.3 为什么合成一个 `engine` 库而不是拆成三个

拆成 core / platform / render 三个 target 会让 core 反向依赖 platform
（因为 console / mutex 的实现文件在 platform 目录下）。与其制造一个假的
依赖图，不如合成一个库，靠**目录约定 + 代码审查**保证分层。

等 M5 之后模块多了、依赖关系稳定了，再考虑拆分。

### 1.4 系统库依赖

| 库 | 用途 |
|---|---|
| `opengl32` | GL 1.1 导入函数 + `wglGetProcAddress` |
| `user32` | 窗口、消息、DPI、光标 |
| `gdi32` | `ChoosePixelFormat` / `SetPixelFormat` / `DescribePixelFormat` / `SwapBuffers` |
| `winmm` | `timeBeginPeriod`（提升系统计时器精度） |

`winmm` 只用到两个函数，所以 `win32_time.c` 里直接声明原型，
不把整个 `mmsystem.h` 拖进来。

## 二、窗口

### 2.1 全屏用"无边框窗口铺满显示器"，不用独占全屏

| 方案 | 优点 | 缺点 |
|---|---|---|
| `ChangeDisplaySettingsEx` 独占全屏 | 延迟略低 | alt-tab 要重排分辨率、会黑屏；调试时被切成 640x480 会卡住；多显示器行为难预期 |
| **无边框窗口铺满显示器**（采用） | alt-tab 快、不改桌面分辨率、多显示器行为可预期 | 没有独占全屏那一点点延迟优势 |

对一个从 M1 要走到 M14 的项目，"调试时不会被分辨率切换卡住"比那点延迟重要得多。

### 2.2 全屏状态必须完整保存与还原

进入全屏前保存 `GWL_STYLE` / `GWL_EXSTYLE` / `GetWindowRect` / `GetWindowPlacement`，
退出时逐项还原。只保存尺寸是不够的 —— 窗口可能处于最大化状态，
用 `SetWindowPlacement` 才能正确恢复"最大化 + 原始位置"。

### 2.3 鼠标锁定用"裁剪 + 每帧回中"，不用 Raw Input

锁定模式下的目标是把鼠标位移变成**不受窗口边界限制的无限位移**（FPS 视角）。

采用方案：`ClipCursor` 限制在客户区 + 每帧 `SetCursorPos` 回中心 +
位移 = 当前位置 − 中心。

* 优点：实现简单，不需要处理 `WM_INPUT` 的消息路径。
* 缺点：位移经过系统的鼠标加速曲线，且分辨率受限于屏幕像素。

**Raw Input（`RegisterRawInputDevices` + `WM_INPUT`）能拿到未经加速的原始位移**，
是更正确的做法。这属于 M9"输入增强"的范围，届时替换。

两个必须处理的细节：
1. **刚锁定时要丢弃第一条 `WM_MOUSEMOVE`**。光标可能还在窗口另一头，
   那一次的位移是"从旧位置跳到中心"的假位移，不丢弃会让视角瞬间甩出去。
2. **窗口尺寸变化时要重新 `ClipCursor`**。否则裁剪矩形还是旧尺寸，
   光标会被限制在一个错误的区域里。

### 2.4 销毁窗口前必须 `ClipCursor(NULL)`

不释放裁剪的话，**整个系统的光标会被永久限制在已销毁窗口的矩形内**。
这个 bug 的表现是"程序退出了但鼠标只能在一个小方块里动"，
用户只能注销或重启才能恢复。

### 2.5 DPI 感知必须在创建任何窗口之前设置

`SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` 调用晚了，窗口会先以
96 DPI 的逻辑尺寸建好，之后系统做位图拉伸 —— 表现为画面发虚、
鼠标坐标与像素对不上。

另外注意：**给 `CreateWindowExW` 的尺寸是"外层窗口尺寸"**，
要先用 `AdjustWindowRectEx` 从期望的客户区尺寸换算过去。
不做这一步，请求 1280x720 得到的是"含边框 1280x720"，客户区只有 1264x681。

### 2.6 `WM_CLOSE` 里只标记，不 `DestroyWindow`

如果在 `WM_CLOSE` 里直接 `PostQuitMessage`，上层的清理代码可能来不及跑
（GL 资源要在上下文还活着时删，上下文要在窗口之前销毁）。
现在 `WM_CLOSE` 只设 `should_close`，销毁顺序完全由上层显式控制。

### 2.7 `WM_SYSKEYDOWN` 必须返回 0

交给 `DefWindowProc` 的话，系统会把它当成"激活系统菜单"的请求
（F10、Alt 都会触发）。表现为按一下 F10，输入焦点就被菜单抢走。
另外还要在 `WM_SYSCOMMAND` 里吞掉 `SC_KEYMENU`。

### 2.8 `WM_ERASEBKGND` 返回 1

不返回 1 的话，每次尺寸变化系统都会用背景刷涂一遍，
在 OpenGL 窗口上会看到白色闪烁。

## 三、输入

### 3.1 双缓冲（current / previous）是边沿检测的唯一实现方式

`input_begin_frame` 把 current 拷进 previous，之后 current 才接收本帧事件。

| 查询 | 含义 |
|---|---|
| `input_key_down` | 当前是否按着 |
| `input_key_pressed` | 这一帧刚按下 |
| `input_key_released` | 这一帧刚松开 |

**已知局限**：一帧内"按下又松开"最终状态是"没按下"，previous 也是"没按下"，
两个边沿都检测不到。这个行为写进了测试
（`press_and_release_within_one_frame_is_lost`）以免将来有人误以为它能工作。
需要"瞬间点按"的场景应当靠 M9 的输入事件队列解决。

### 3.2 失焦时必须清空按键状态，且要产生 released 边沿

窗口失去焦点时系统不会补发 `KEYUP`。不清空的话，玩家 alt-tab 出去再回来，
那个键会永远是"按下"状态。

`input_clear_all` 的实现是**先把 current 快照进 previous，再清空 current**：

```c
memcpy(state->keys_previous, state->keys, sizeof(state->keys));
memset(state->keys, 0, sizeof(state->keys));
```

这样保证"所有当时按着的键，本帧一定会产生一次 released 边沿"，
与失焦发生在帧内哪个时刻无关。

**这里踩过一次**：最初只清 current 不更新 previous，那么当"按下"和"失焦"
发生在同一帧时，previous 里还是更早的状态（0），released 边沿不会产生 ——
"按住鼠标拖拽时 alt-tab 出去"会让拖拽逻辑永远收不到结束事件，
物品一直粘在光标上。

### 3.3 按键枚举用自己的，不用 Win32 虚拟键码

用 `VK_*` 做枚举值会让平台细节渗进每一处游戏逻辑，将来接 Linux/macOS 全要改。
引擎定义自己的 `key_t`，映射表放在 `win32_input.c`。

### 3.4 映射表只写一份，反向表推导出来

`s_vk_to_key[256]` 用 C99 设计初始化器写成唯一事实来源，
`s_key_to_vk` 在首次使用时从它构建。

写两份表的项目迟早会出现"按 W 触发 S"这种 bug —— 而且这种 bug 不会崩，
只会让人怀疑自己的键盘。

### 3.5 修饰键的左右区分

`WM_KEYDOWN` 对修饰键给的是**通用**虚拟键码（`VK_SHIFT` / `VK_CONTROL` / `VK_MENU`），
不区分左右。区分方式：

| 键 | 依据 |
|---|---|
| Shift | 扫描码（0x2A 左 / 0x36 右），用 `MapVirtualKeyW(sc, MAPVK_VSC_TO_VK_EX)` |
| Ctrl / Alt | `lParam` 位 24 的 extended 标志 |

不区分的话，重绑定界面会出现"给左 Shift 绑了键，按右 Shift 也触发"。

### 3.6 小键盘回车不是主回车

小键盘回车是"扩展键"（`lParam` 位 24 为 1），主键盘回车不是。
不区分的话两者会互相覆盖。同理小键盘除号也是扩展键。

### 3.7 `input_push_*` 是公开 API，不只是内部接口

用途：
* 平台层从 `WndProc` 推事件；
* **单元测试可以脱离窗口构造任意输入序列** —— 这是输入逻辑能被可靠测试的前提；
* M9 的"输入录制/回放"直接把录下来的事件序列重放进来。

## 四、计时

### 4.1 计时用 `QueryPerformanceCounter`

`QueryPerformanceFrequency` 的结果在进程生命周期内恒定，缓存一次。
每帧都调用它属于纯浪费。

### 4.2 帧率稳定靠两条路，优先 vsync

1. **垂直同步**（`wglSwapIntervalEXT(1)`）：`SwapBuffers` 阻塞到下一次刷新，
   帧率天然锁在显示器刷新率上，且没有撕裂。**首选**。
2. **帧率限制器**：vsync 关闭（测性能）时才用。

实测（NVIDIA RTX 5060，1280x720，300 帧）：

| 模式 | 平均帧时间 | 最大帧时间 | 平滑 FPS |
|---|---|---|---|
| vsync 开 | 16.665 ms | 19.210 ms | 60.0 |
| vsync 关 + 限制器 | 16.670 ms | 16.723 ms | 60.0 |

### 4.3 帧率限制器为什么不能简单 `Sleep(剩余毫秒)`

Windows 默认的系统计时器精度是 **15.6ms**。`Sleep(16)` 可能睡 16ms，
也可能睡 31ms，帧率会剧烈抖动。

两步解决：

1. `platform_time_init(true)` 调 `timeBeginPeriod(1)` 把精度提到 1ms。
   Win10 2004 起这个设置是**进程级**的，不再拖累整个系统。
2. 最后 `spin_margin_ms` 那段时间**忙等**（`YieldProcessor`）而不是 Sleep。
   Sleep 无法精确到亚毫秒。

`spin_margin_ms` 是自适应的：高精度计时器生效时 1.5ms，
未生效时 16ms（此时 Sleep 完全不可靠，只能靠忙等，代价是烧 CPU）。
所以**强烈建议开高精度计时器**。

忙等的代价：1.5ms / 16.67ms ≈ 单核 9% 的 CPU。可接受。

### 4.4 `frame_clock_tick_at` 是为了可测试性

`frame_clock_tick()` 内部取系统时间，测不了。
`frame_clock_tick_at(clock, 时间点)` 接受显式时间点，测试可以喂合成时间序列，
验证 delta / FPS / 极值统计的边界条件，而不用真的等 1 秒。

同理 `frame_limiter_remaining_ms` 是纯函数（只算数不碰时钟），
它的边界条件（超预算返回 0 而不是负数）可以被完整测试。

### 4.5 第一帧的 delta 不能代表帧耗时

`frame_clock_init` 里 `previous = current = now`，所以第一次 tick 的 delta
是"初始化到进入循环"的时间。做法是在进入循环前调 `frame_clock_reset()`，
让第一帧的 delta 就是真实帧耗时。

### 4.6 窗口标题不要每帧更新

`SetWindowTextW` 要过一遍消息队列，实测能吃掉几百微秒。
示例里每 0.25 秒更新一次。

## 五、OpenGL 加载

### 5.1 为什么自己写 loader 而不用 glad

| 理由 | 说明 |
|---|---|
| 可读 | glad 是生成出来的几万行代码，出问题只能对着生成器配置看 |
| 规模可控 | M1 只需要约 60 个函数，X-macro 维护一份清单，增删都是改一行 |
| 诊断可控 | glad 只把指针留成 NULL，用起来才发现段错误；这里加载时就逐个报告 |
| 没有隐藏全局 | glad 用宏重定义符号名（`#define glClear glad_glClear`），排查时很折磨人 |

代价：新用到某个 GL 函数时必须手动加进清单。换来的是"引擎用到的 GL 表面"
完全显式。

### 5.2 X-macro 一份清单生成三处代码

```c
#define GL_FUNCTION_LIST(X) \
    X(void, glClear, (GLbitfield mask)) \
    ...

// 1) 结构体成员  2) 加载代码  3) 缺失函数的日志
```
加函数只需在清单里加一行。

注意每项的第三个参数**必须带外层括号**，否则参数里的逗号会被当成宏分隔符。

### 5.3 Win32 上加载 GL 的四个坑

1. Windows 自带的 `opengl32.dll` **只导出 OpenGL 1.1**。1.2 以上的函数
   必须用 `wglGetProcAddress` 逐个取。
2. `wglGetProcAddress` **只对扩展/1.2+ 函数有效**，对 1.1 函数返回 NULL。
   取不到时必须回退到 `GetProcAddress(opengl32.dll)`。
3. **某些驱动在函数不存在时返回 1 / 2 / 3 / -1 这些"假指针"**而不是 NULL。
   不判这几个值，会在调用时跳到非法地址直接崩。
4. `wglGetProcAddress` **需要一个 current 的上下文**，否则一律返回 NULL。
   所以加载必须发生在 `gl_context_create` 之后。

### 5.4 调用约定

Win32 下 GL 函数是 `__stdcall`（`APIENTRY`）。x86 上写成默认的 `__cdecl`
会导致栈失衡，**而 x64 上两者等价，所以本地 x64 开发时完全测不出这个错**。
函数表里每个成员都带 `GLAPI` 宏。

### 5.5 不包含 `<GL/gl.h>`

系统头文件只声明 1.1 的函数，且用的是导入库方式。同时包含会出现两套同名符号
（一套是导入函数、一套是我们的函数指针），链接冲突且极难排查。
所以 `gl_types.h` 自己定义类型和常量，完全不碰系统的 GL 头文件。

### 5.6 `gl_check_error` 只在 Debug 下调用

`glGetError` 会强制刷新命令队列，每帧调用是有成本的。
`GL_CHECK()` 宏在 Release 下编译成 `((void)0)`。

## 六、OpenGL 上下文

### 6.1 必须两阶段创建

Windows 上拿 4.5 上下文必须靠 WGL 扩展
（`wglChoosePixelFormatARB` / `wglCreateContextAttribsARB` / `wglSwapIntervalEXT`），
而这些函数指针**必须先有一个 current 的 GL 上下文**才能用 `wglGetProcAddress` 取到。

```
阶段 1（引导）：临时窗口 + 1.1 legacy context → 取到三个 WGL 扩展函数指针
阶段 2（正式）：销毁引导窗口 → 在真实窗口上挑像素格式 → 创建 4.5 core context
                → make current → 加载函数表
```

**引导窗口和正式窗口必须是两个不同的窗口** —— `SetPixelFormat` 对同一个窗口
只能成功调用一次，而两阶段需要的像素格式不同。

### 6.2 引导阶段必须先解绑再销毁

```c
wglMakeCurrent(NULL, NULL);
wglDeleteContext(rc);
platform_window_destroy(dummy);
```

顺序反了会让"销毁窗口"顺手失效掉当前上下文，产生难查的副作用。

### 6.3 `wglChoosePixelFormatARB` 失败要降级重试

请求 MSAA 但驱动不支持时，它返回 **0 个可用格式**，而不是返回一个
"不带 MSAA 的格式"。所以必须自己去掉 MSAA 重试，而不是直接失败。

### 6.4 `DescribePixelFormat` 的输出要手动补标志

某些驱动的 `DescribePixelFormat` 会漏写 `PFD_SUPPORT_OPENGL` /
`PFD_DOUBLE_BUFFER` / `PFD_DRAW_TO_WINDOW`，直接拿它去 `SetPixelFormat` 会失败。

```c
pfd.dwFlags |= PFD_DRAW_TO_WINDOW | PFD_SUPPORT_OPENGL | PFD_DOUBLEBUFFER;
```

### 6.5 版本请求要逐级降级，并报告实际拿到什么

驱动可能不支持请求的版本。直接失败对使用者毫无帮助；
逐级降级（4.5 → 4.3 → 3.3 → 3.2）并打 WARN 报告实际版本才有用。

版本号最终以驱动报告的 `GL_MAJOR_VERSION` / `GL_MINOR_VERSION` 为准
（可能比请求值高）。

### 6.6 调试上下文打开 `GL_KHR_debug`

`glDebugMessageCallback` 把 GL 错误从"某个调用返回 0"变成
"哪一行、什么类型、什么严重级别"，这是 M1 最值钱的一个开关。

`GL_DEBUG_SEVERITY_NOTIFICATION` 级别必须过滤掉 —— 它会把每一处 API 细节
都吐出来（包括无害的冗余状态设置），开着它日志会被淹没。

销毁上下文前要**先关掉调试输出**，否则销毁过程中触发的 GL 消息会在
日志系统已经关闭之后才回调进来。

## 七、本阶段踩到的坑

### 7.1 着色器源码缓冲区截断，报的是"语法错误"

`snprintf` 把 180 多字节的着色器正文截断到 128 字节，驱动报：

```
error C0000: syntax error, unexpected $end, expecting "::" at token "<EOF>"
```

看起来像着色器语法写错了，实际上是源码根本没传完整。
**截断错误永远不会指向真正的原因。**

修法：缓冲区开到 1024，并用 `snprintf(NULL, 0, ...)` 的返回值显式验证
"本该写入的长度"是否超出缓冲区。

### 7.2 `input_clear_all` 只清 current 会产生不了 released 边沿

见 3.2。这个 bug 的表现是"按住鼠标拖拽时 alt-tab 出去，物品粘在光标上"。

### 7.3 `goto cleanup` 跳过的变量是未初始化的

示例里 `frames_rendered` 声明在若干个 `goto cleanup` 之后，
clang 报 `-Wsometimes-uninitialized`。所有会被 `cleanup` 用到的变量
都必须声明在**第一个 goto 之前**并初始化。

### 7.4 `ARENA_NEW` 只能用在 arena 上

示例里一开始写成 `ARENA_NEW(allocator_heap(), platform_window_t)` ——
`allocator_heap()` 返回的是 `allocator_t*`，而 `ARENA_NEW` 需要 `arena_t*`。
类型不匹配会直接编译失败，但这个错误提示容易让人以为"宏写错了"。
窗口这类永久对象直接用 `alloc->alloc()` + 显式 `free()`。

## 八、M1 遗留问题 / 已知代价

| 项 | 现状 | 计划 |
|---|---|---|
| 鼠标位移经过系统加速曲线 | 用裁剪 + 回中实现锁定 | M9 换 Raw Input |

## 九、给后续阶段的提醒

1. **M2 的 `render_backend_t` 必须按 Vulkan 语义设计**（显式 render pass、
   显式资源布局、不可变 pipeline state object、显式同步），GL 实现内部做
   状态机降级适配。如果按 GL 的直觉设计，M13 会变成重写渲染层。
2. **M2 结束时就把 `gl_types.h` / `gl_api.h` 的清单补全**，
   并且把"引擎用到的 GL 表面"当作后端抽象的设计输入 ——
   清单里的每一项都是未来 `render_backend_t` 需要覆盖的能力。
3. **`GL_CHECK()` 在 Debug 下要勤用**，但别放进每帧的热路径循环里。
4. **深度范围约定（[0,1]）已经在 M0 定死**，M2 的投影矩阵直接用
   `mat4_perspective` / `mat4_ortho`，不要自己再写一份。
5. **`platform_time_is_high_resolution()` 决定帧率限制器的行为**，
   如果将来在别的平台实现，记得一起提供。
